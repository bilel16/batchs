Charger tous les engagements des parties liées en une seule requête batch (IN clause)

Au lieu de N requêtes pour N actionnaires/vendeurs, une seule requête avec WHERE id IN (...)

PRIORITÉ HAUTE 2-3h Oracle 11g ✓
⚠️
Oracle 11g limite : La clause IN supporte jusqu'à 1000 valeurs par liste. Pour des cas rares avec plus de 1000 éléments, diviser en sous-listes. Dans la pratique pour ce projet, le nombre de parties liées sera toujours bien en dessous de 1000.

Principe : collecter tous les IDs puis une seule requête

// CanevasSnapshotService.java — méthode buildFullEngagementDetailleJson()

// ─── ÉTAPE 1 : Collecter tous les numSeqPers en une passe ───
List<Associe> actionnaires = associeRepository.findAssociesByNumSeqPers(numSeqPers);
Optional<ClientCanvas> respOpt = clientCanvasRepository.findByNumSeqpers(numSeqPers);
List<GroupeDTO> groupes = clientService.getListeGroupesByNumGRP(codGrp);
List<Vendeur> vendeurs = getVendeurs(caneva);

// Rassembler tous les IDs de personnes dont on a besoin
Set<String> allNumSeqPers = new HashSet<>();
actionnaires.stream().map(a -> String.valueOf(a.getNumSeqpers())).forEach(allNumSeqPers::add);
respOpt.map(r -> String.valueOf(r.getNumSeqpers())).ifPresent(allNumSeqPers::add);
groupes.stream().map(GroupeDTO::getNumSeqPers).forEach(allNumSeqPers::add);
vendeurs.stream().map(v -> String.valueOf(v.getNumSeqpers())).forEach(allNumSeqPers::add);

// ─── ÉTAPE 2 : UNE SEULE requête pour tous les engagements BNA ───
Map<String, List<EngagementBNADTO>> bnaByPers =
    engagementService.getEngagementsBNABatch(allNumSeqPers);
// clé = numSeqPers, valeur = liste de ses engagements

Map<String, List<ClasseDTO>> classBnaByPers =
    engagementService.getClasseBNABatch(allNumSeqPers);

// ─── ÉTAPE 3 : Construire les DTO avec les données déjà en mémoire ───
List<EngagementPartieDto> actionnairesDto = actionnaires.stream()
    .map(a -> EngagementPartieDto.builder()
        .nom(a.getNom())
        .engagementsBNA(bnaByPers.getOrDefault(String.valueOf(a.getNumSeqpers()), List.of()))
        .classeBNA(classBnaByPers.getOrDefault(String.valueOf(a.getNumSeqpers()), List.of()))
        .build())
    .collect(Collectors.toList());
// ZÉRO requête SQL dans cette boucle !

public Map<String, List<EngagementBNADTO>>
    getEngagementsBNABatch(Set<String> numSeqPersList) {

  if (numSeqPersList.isEmpty()) return Map.of();

  Map<String, List<EngagementBNADTO>> result = new HashMap<>();

  // Initialiser chaque clé avec une liste vide
  numSeqPersList.forEach(id -> result.put(id, new ArrayList<>()));

  // Charger chaque type en batch (IN clause) — compatible Oracle 11g
  addEngagementFCDPBatch(result, numSeqPersList);
  addEngagementCMEBatch(result, numSeqPersList);
  addEngagementINVBatch(result, numSeqPersList);
  // ... etc pour les 8 types

  return result;
}

Créer une vue Oracle (recommandé)

-- Script SQL Oracle 11g à exécuter une fois
-- Fichier : create_view_engagements_bna_unified.sql

CREATE OR REPLACE VIEW V_ENGAGEMENTS_BNA_UNIFIED AS
  SELECT NUM_SEQ_PERS, 'FCDF' AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_FCDF_VIEW
  UNION ALL
  SELECT NUM_SEQ_PERS, 'CME'  AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_CME_VIEW
  UNION ALL
  SELECT NUM_SEQ_PERS, 'EPS'  AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_EPS_VIEW
  UNION ALL
  SELECT NUM_SEQ_PERS, 'ESC'  AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_ESC_VIEW
  UNION ALL
  SELECT NUM_SEQ_PERS, 'INV'  AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_INV_VIEW
  UNION ALL
  SELECT NUM_SEQ_PERS, 'BPN'  AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_BPN_VIEW
  UNION ALL
  SELECT NUM_SEQ_PERS, 'AGR'  AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_AGR_VIEW
  UNION ALL
  SELECT NUM_SEQ_PERS, 'SBE'  AS TYPE_ENG, MONTANT_ENG, NUM_CPT, DT_OCTROI
    FROM SAEB.ENG_SBE_VIEW;

JOIN FETCH pour le chargement du Caneva et ses relations

Charger le Caneva avec toutes ses collections en une requête au lieu de déclencher le lazy loading

PRIORITÉ MOYENNE 1-2h Oracle 11g ✓

Quand canevaRepository.findById(id) est appelé dans createSnapshot(), les collections creditAchatTerrains, creditInvestissements, creditCourtTermes, selectedSites sont en LAZY — chaque accès déclenche une requête SQL séparée.

Ajouter une requête avec JOIN FETCH dans CanevaRepository

// CanevaRepository.java — ajouter cette méthode

@Query("SELECT DISTINCT c FROM Caneva c " +
       "LEFT JOIN FETCH c.creditCourtTermes " +
       "LEFT JOIN FETCH c.creditInvestissements " +
       "LEFT JOIN FETCH c.creditAchatTerrains cat " +
       "LEFT JOIN FETCH cat.vendeurs " +  // charge les vendeurs en même temps
       "LEFT JOIN FETCH c.selectedSites " +
       "WHERE c.id = :id")
Optional<Caneva> findByIdWithAllRelations(@Param("id") Long id);

Utiliser dans CanevasSnapshotService

// CanevasSnapshotService.java — méthode createSnapshot()

// AVANT
Caneva caneva = canevaRepository.findById(canevasId)
    .orElseThrow(...);  // lazy loading sur chaque accès

// APRÈS
Caneva caneva = canevaRepository.findByIdWithAllRelations(canevasId)
    .orElseThrow(...);  // tout chargé en UNE requête SQL avec JOINs
ℹ️
DISTINCT obligatoire : Avec plusieurs JOIN FETCH, JPA peut multiplier les résultats. SELECT DISTINCT garantit un seul objet Caneva en retour, même avec plusieurs collections jointes.
Gain estimé :
−4 à −6 requêtes lazy supprimées

Créer le snapshot en arrière-plan (asynchrone)

L'utilisateur reçoit la réponse HTTP immédiatement, le snapshot se crée en tâche de fond

PRIORITÉ MOYENNE 2h Oracle 11g ✓
⚠️
Cette solution améliore la perception de lenteur par l'utilisateur, mais ne réduit pas le nombre de requêtes SQL. À combiner avec les solutions 1-3 pour un effet maximal. Attention : si le snapshot échoue en arrière-plan, il faut une stratégie de notification d'erreur.

Architecture : répondre vite, créer en arrière-plan

// AvisController.java

@PostMapping("/avis")
public ResponseEntity<AvisResponseDTO> saveAvis(@RequestBody AvisDTO avisDto) {

    // 1. Sauvegarder l'avis et mettre à jour le canevas (rapide)
    Avis avis = avisService.saveAvis(avisDto);          // 6 req seulement
    avisService.updateCaneva(avisDto);
    avisService.createAffectation(avisDto);

    // 2. Lancer la création du snapshot en arrière-plan
    snapshotService.createSnapshotAsync(avisDto.getCanevasId(), avisDto);

    // 3. Répondre IMMÉDIATEMENT à l'utilisateur
    return ResponseEntity.ok(new AvisResponseDTO(avis.getId(), "ENREGISTRE"));
    // ↑ L'utilisateur ne patiente plus les 100+ requêtes !
}

Méthode asynchrone Spring

// CanevasSnapshotService.java

@Async            // ← exécuté dans un thread séparé
@Transactional    // ← sa propre transaction
public CompletableFuture<Void> createSnapshotAsync(Long canevasId, AvisDTO dto) {
    try {
        createSnapshot(canevasId, dto, "PEC_AVIS_DEC");
    } catch (Exception e) {
        log.error("Snapshot async échoué pour canevas {}: {}", canevasId, e.getMessage());
        // Enregistrer l'erreur pour retry ou alerte
    }
    return CompletableFuture.completedFuture(null);
}

Projection DTO pour la liste historique (sans charger les CLOB)

La liste des snapshots n'a pas besoin des 10 colonnes CLOB — ne charger que les métadonnées

PRIORITÉ BASSE 1h Oracle 11g ✓

Quand l'historique est affiché (onglet Snapshots), le backend charge toute l'entité CanevasStructureSnapshot incluant les 10 champs CLOB (JSON volumineux). Ces données ne sont pas utilisées dans la liste.
