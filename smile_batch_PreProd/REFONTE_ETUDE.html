1. Analyse de l'existant Forces & Limites

Ce que l'application fait bien (à conserver)

✅

Logique métier solide

Les Moulinettes (Effet, Chèque, Prélèvement) encapsulent une logique de compensation bancaire éprouvée et correcte.

✅

Progression en temps réel

Le tableau agence par agence avec états (EN COURS / TERMINÉ / ERREUR) est un concept UX pertinent à moderniser.

✅

Traçabilité (TraceBatch)

Enregistrement des traces d'exécution avec heure début/fin dans Oracle — bonne pratique à amplifier.

✅

Séparation insertion/position

Le cycle en 2 phases (Lecture Fichier → Position) est un processus métier correct et sécurisé.

Les limites bloquantes de l'application Swing

ProblèmeImpactSévérité
Mono-poste obligatoire — l'application tourne sur un seul PC connecté à Oracle Un seul opérateur peut travailler. Impossible de suivre à distance. Critique
Contexte Spring rechargé à chaque clic — 14 fichiers XML relus à chaque traitement Lenteur de 3 à 10 secondes avant chaque traitement Élevé
Pas d'authentification — n'importe qui sur le poste peut lancer un traitement Risque sécurité majeur sur des opérations bancaires critiques Critique
Pas d'audit trail — on sait si ça a marché mais pas qui a lancé quoi ni quand précisément Non conforme aux exigences réglementaires bancaires Critique
Pas de retry automatique — une erreur sur une agence bloque et désactive la position Intervention manuelle systématique, perte de temps en production Élevé
Aucune notification — l'opérateur doit rester devant l'écran jusqu'à la fin Immobilisation de l'opérateur pendant 30 à 60 minutes Élevé
Rapports JasperReports locaux — fichiers .jasper sur le poste, PDF sauvegardé localement Perte possible de rapports, pas d'historique centralisé Élevé
Impossible de planifier — tout est manuel, pas de lancement automatique Dépendance totale à la présence physique d'un opérateur Élevé
Maintenance difficile — Java Swing, OXIA Framework propriétaire, Spring XML legacy Peu de développeurs maîtrisent ce stack en 2026 Moyen
Pas de statistiques historiques — impossible de comparer J vs J-1 ou de détecter des anomalies Aucune visibilité analytique sur les volumes de compensation Moyen

🎯 Vision : de l'outil mono-poste à la plateforme de supervision bancaire La refonte ne doit pas simplement "traduire" Swing en Angular. Elle doit transformer BatchFrame en une plateforme web de pilotage de la télé-compensation, accessible depuis n'importe quel poste du réseau BNA, avec supervision en temps réel, historique, alertes et planification automatique.

Les 3 axes de justification

🔒

Axe Sécurité & Conformité

Authentification JWT, audit trail complet, RBAC (rôles : Opérateur / Superviseur / Admin), journalisation de chaque action.

🌐

Axe Accessibilité & Disponibilité

Application web accessible depuis tout le réseau BNA. Supervision possible depuis n'importe quel poste sans installation.

📈

Axe Productivité & Automatisation

Planification des traitements (CRON), retry automatique, notifications e-mail/SMS, tableau de bord analytique.

4. Idées innovantes Fonctionnalités nouvelles

📡

Tableau de bord temps réel (WebSocket)

Plus de page à rafraîchir manuellement. Chaque changement d'état d'une agence (EN COURS → TERMINÉ → ERREUR) est poussé instantanément via STOMP/WebSocket vers tous les navigateurs connectés.

WebSocket STOMP Angular Signal Temps réel
🤖

Planification automatique (Scheduler UI)

L'opérateur configure depuis l'interface un CRON : "lancer l'insertion Effet tous les jours à 06h30". Plus besoin d'être présent. Le batch se lance seul et envoie un email de résultat.

Quartz Scheduler CRON Builder Email notif
🔁

Retry automatique & reprise sur erreur

Spring Batch gère nativement la reprise. Si l'agence 205 échoue, le job peut être relancé uniquement depuis l'agence 205, sans tout rejouer. Configuration du nombre de tentatives depuis l'UI.

Spring Batch Retry Skip Policy Restart Job
🔔

Système d'alertes multi-canal

Fin de traitement, erreur critique, dépassement de seuil (ex: montant total > X MDT) → notification automatique par email ET par notification push navigateur. Configurable par utilisateur.

JavaMail Browser Push Thresholds
📊

Analytics & Tendances historiques

Graphiques interactifs : évolution des volumes jour par jour, comparaison semaine actuelle vs semaine précédente, top 5 agences par montant, détection d'anomalies (pic ou creux inhabituel).

Chart.js Oracle Analytics PrimeNG Charts
🗂️

Gestionnaire de rapports centralisé

Tous les PDFs générés sont stockés et indexés côté serveur. L'utilisateur peut consulter n'importe quel rapport des 90 derniers jours depuis son navigateur, sans accès au serveur de fichiers.

Stockage serveur PDF Viewer Historique 90j
🎛️

Mode Simulation (Dry Run)

Avant de lancer un traitement réel, l'opérateur peut simuler l'exécution sans écrire en base. Le système lit les fichiers, calcule les volumes et affiche un résumé sans modifier Oracle. Idéal pour validation.

Dry Run Mode Validation préalable Zéro risque
🔐

Audit Trail & Traçabilité complète

Chaque action (lancement, arrêt, consultation, export) est journalisée : qui, quand, depuis quelle IP, durée, résultat. Rapport d'audit consultable et exportable. Conforme exigences réglementaires BCT.

Aspect AOP Table AUDIT_LOG Export Excel
💡 Idée avancée : Indicateur de santé du batch (Health Score) Un score sur 100 calculé en temps réel : nombre d'agences traitées sans erreur / nombre total. Si le score descend sous 80% → alerte automatique envoyée au superviseur. Affiché en grand sur le dashboard avec code couleur (vert / orange / rouge).

Spring Batch — remplacement des Moulinettes

Principe : Moulinette → Spring Batch Job Chaque "Moulinette" (MoulinetteCompensationEffetTest, etc.) devient un Spring Batch Job avec des Steps. Spring Batch apporte nativement : gestion des erreurs, restart depuis le point d'échec, statistiques d'exécution, historique en base.
Ancien (Swing Thread)Nouveau (Spring Batch)Bénéfice
new Thread(new MoulinetteEffetTest()).start() jobLauncher.run(effetInsertionJob, params) Restart, monitoring, historique automatique
Boucle for agence par agence (manuelle) Spring Batch Step avec ItemReader / ItemProcessor / ItemWriter Chunk processing, retry, skip configurables
frame.addOrUpdateEtat(infoVo) (Swing) simpMessagingTemplate.convertAndSend("/topic/progress", msg) (WebSocket) Multi-utilisateurs, navigateur en temps réel
Spring context rechargé à chaque clic ApplicationContext Spring chargé 1 seule fois au démarrage Démarrage batch en millisecondes

Exemple : BatchLauncherService.java

@Service
@Slf4j
public class BatchLauncherService {

    @Autowired private JobLauncher jobLauncher;
    @Autowired private Job effetInsertionJob;
    @Autowired private WebSocketNotifService wsNotif;
    @Autowired private AuditService auditService;

    public BatchExecutionDto lancerBatch(BatchRequest request, String username) {
        // 1. Audit : qui lance quoi
        auditService.log(username, "BATCH_LAUNCH", request.getInstrument() + "/" + request.getPhase());

        // 2. Paramètres du job
        JobParameters params = new JobParametersBuilder()
            .addString("instrument", request.getInstrument())
            .addString("phase", request.getPhase())
            .addLong("timestamp", System.currentTimeMillis())
            .toJobParameters();

        // 3. Notifier Angular du démarrage (WebSocket)
        wsNotif.broadcastStatus("STARTED", request.getInstrument(), 0);

        // 4. Lancer le job en arrière-plan
        JobExecution exec = jobLauncher.run(effetInsertionJob, params);

        return BatchExecutionDto.from(exec);
    }
}

public class WebSocketNotifService {

    @Autowired
    private SimpMessagingTemplate messagingTemplate;

    // Appelé par Spring Batch StepListener à chaque agence traitée

        messagingTemplate.convertAndSend("/topic/batch/progress", msg);

Service WebSocket Angular (STOMP)

// websocket.service.ts
@Injectable({ providedIn: 'root' })
export class WebSocketService {

  private client = signal<Client | null>(null);
  readonly agenceProgress = signal<AgenceProgress[]>([]);
  readonly batchStatus = signal<BatchStatus | null>(null);

  connect() {
    const stompClient = new Client({
      brokerURL: `ws://localhost:8000/ws`,
      onConnect: () => {
        // S'abonne aux mises à jour de progression
        stompClient.subscribe('/topic/batch/progress', msg => {
          const data = JSON.parse(msg.body) as AgenceProgress;
          this.agenceProgress.update(list => {
            const idx = list.findIndex(a => a.structure === data.structure);
            return idx >= 0
              ? list.map((a, i) => i === idx ? data : a)
              : [...list, data];
          });
        });
        // S'abonne au statut global
        stompClient.subscribe('/topic/batch/status', msg => {
          this.batchStatus.set(JSON.parse(msg.body));
        });
      }
    });
    stompClient.activate();
    this.client.set(stompClient);
  }
}

Conclusion La refonte de BatchFrame vers Spring Boot + Angular est une transformation à fort ROI. Elle ne se limite pas à un changement de technologie UI : elle convertit un outil mono-poste sans sécurité en une plateforme de supervision bancaire moderne, multi-utilisateurs, temps réel, sécurisée et automatisable. La logique métier (Moulinettes) est conservée et renforcée par Spring Batch, garantissant la continuité des traitements de télé-compensation sans risque de régression fonctionnelle.
