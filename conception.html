C'est quoi la « conception » d'une application ?

La conception, c'est comme le plan d'architecte d'une maison avant de la construire. On décide : comment les pièces (modules) sont organisées, comment elles communiquent entre elles, où on stocke les données, et qui a accès à quoi. Un bon plan évite les problèmes plus tard.

Architecture en couches — Principe fondamental

Règle d'or : Chaque couche ne parle qu'à la couche directement en dessous ou au-dessus d'elle. Le Controller ne parle pas au Repository. Le Component Angular ne parle pas directement à la base Oracle. Cette séparation s'appelle le principe de séparation des responsabilités.

Les 7 couches de l'application (de l'utilisateur à la base de données)

🖥️ Couche 1 — Component Angular frontend-app1/src/app/_components/
Rôle : Afficher les données à l'utilisateur et capturer ses actions (clic, saisie de formulaire).
Ce qu'elle fait : Appelle le Service Angular quand l'utilisateur agit. Reçoit les données et les affiche dans le template HTML.
Ce qu'elle NE fait PAS : Elle ne contient pas de logique HTTP ni de traitement des données.
// Exemple : list.component.ts ngOnInit() { this.canevasService.getAllCanevas() .subscribe(data => this.canevas = data); // ← reçoit, affiche }
↕
⚡ Couche 2 — Service Angular frontend-app1/src/app/_services/
Rôle : Communiquer avec le backend via HTTP. C'est le "messager" entre Angular et Spring Boot.
Ce qu'elle fait : Construit les requêtes HTTP (GET, POST, PUT, DELETE). Retourne un Observable au Component.
Ce qu'elle NE fait PAS : Elle ne gère pas l'affichage ni la logique métier.
// Exemple : canevas.service.ts getAllCanevas(): Observable<Caneva[]> { return this.http.get<Caneva[]>(`${this.api}api/canevas`); }
↕ HTTP/JSON
🔌 Couche 3 — Controller Java (REST) backend-saeb/.../web/
Rôle : Point d'entrée du backend. Reçoit les requêtes HTTP, les valide et délègue au Service Java.
Ce qu'elle fait : Définit les URLs (/api/canevas), les méthodes HTTP (GET, POST…). Convertit la requête et la réponse.
Ce qu'elle NE fait PAS : Elle ne contient pas de logique métier ni d'accès direct à la base de données.
@GetMapping public ResponseEntity<List<CanevaDto>> getAll() { return ResponseEntity.ok(service.findAll()); // délègue }
↕
⚙️ Couche 4 — Service Java (Logique métier) backend-saeb/.../service/
Rôle : Contient toute la logique métier (calculs, validations, règles BNA).
Ce qu'elle fait : Appelle le Repository, transforme Entity ↔ DTO, applique les règles métier.
Ce qu'elle NE fait PAS : Elle ne gère pas les requêtes HTTP.
@Service public class CanevaServiceImpl { public CanevaDto save(CanevaDto dto) { Caneva entity = convertToEntity(dto); // DTO → Entity Caneva saved = repo.save(entity); // sauvegarde return convertToDto(saved); // Entity → DTO } }
↕
📦 Couche 5 — Repository (Accès données) backend-saeb/.../repository/
Rôle : Seule couche qui parle à Oracle. Génère les requêtes SQL automatiquement.
Ce qu'elle fait : Hérite de JpaRepository → Spring génère les SELECT, INSERT, UPDATE, DELETE.
Ce qu'elle NE fait PAS : Elle ne contient pas de logique métier.
public interface CanevaRepository extends JpaRepository<Caneva, Long> { // Spring génère: SELECT * FROM CANEVAS_AGRICOLE WHERE num_seqpers = ? List<Caneva> findByNumSeqpers(Integer num); }
↕ SQL / JDBC
🗄️ Couche 6 — Entité JPA (Modèle) backend-saeb/.../entities/
Rôle : Représentation Java d'une table Oracle. Chaque instance = une ligne de la table.
@Entity @Table(name="CANEVAS_AGRICOLE") public class Caneva { @Id Long id; @Column(name="COD_STRC_DEM") String codeStrcDem; @OneToMany(cascade=ALL) List<CreditCourtTerme> creditsCtTerme; }
↕
🗄️ Couche 7 — Oracle Database
Tables : CANEVAS_AGRICOLE, CREDIT_COURT_TERME, GARANTIE_PROPOSE, AVIS_AGRICOLE, SITES, etc. (40 tables au total).

Relations entre entités — Expliquées simplement

📚 Les 3 types de relations (avec exemples concrets)

OneToMany (1 → N)

Un canevas peut avoir plusieurs crédits court terme. Mais chaque crédit appartient à UN seul canevas.

// Dans Caneva.java @OneToMany(mappedBy="caneva", cascade=ALL) List<CreditCourtTerme> creditsCtTerme;
ManyToOne (N → 1)

Plusieurs crédits court terme peuvent appartenir au même canevas.

// Dans CreditCourtTerme.java @ManyToOne @JoinColumn(name="caneva_id") Caneva caneva; // FK dans la table
ManyToMany (N → N)

Un canevas peut avoir plusieurs sites. Un site peut appartenir à plusieurs canevas.

// Dans Caneva.java @ManyToMany @JoinTable(name="caneva_site_projet") List<Site> selectedSites; // table de jointure

🔄 Gestion de l'état avec Signals Angular 17

Le projet utilise les Signals (nouveauté Angular 17) pour gérer l'état partagé entre composants. C'est plus simple et plus performant que les anciens services avec BehaviorSubject.

// Dans canevas.service.ts // Signal = valeur réactive (comme une variable "intelligente") canevas = signal<Caneva[]>([]); // computed = calculé automatiquement depuis d'autres signals totalCanevas = computed(() => this.canevas().length); // Dans le composant — écoute les changements automatiquement protected canevas = this.canevasService.canevas; // Dans le template HTML <!-- S'actualise automatiquement quand canevas change --> <p>{{ canevas().length }} canevas </p>
Pourquoi les Signals ? Moins de code, meilleure performance, pas de gestion manuelle des subscriptions (plus de risque de memory leaks).

🏗️ Pattern de communication entre composants

@Input — Données du parent vers l'enfant
// Parent envoie des données <app-enfant [donnee]="maVariable"></app-enfant> // Enfant les reçoit @Input() donnee: string;
@Output — Événements de l'enfant vers le parent
// Enfant émet un événement @Output() saved = new EventEmitter(); // Parent écoute <enfant (saved)="onSave($event)"></enfant>
Service partagé — Entre composants non liés
// Service avec signal partagé // Ex: canevasAgrService partage // l'état entre toutes les pages numSeqpers = signal<number>(0); numCanva = signal<number>(0);

Architecture Backend Spring Boot — Conception

🔧 Injection de dépendances (IoC)

Spring Boot gère automatiquement la création des objets. Tu déclares ce dont tu as besoin, Spring te le fournit.

// Sans IoC (mauvais) — crée manuellement public class Controller { private Service service = new ServiceImpl(new Repository()); } // Avec IoC (bien) — Spring injecte automatiquement @RestController public class CanevaController { @Autowired // Spring fournit automatiquement private CanevaService service; }

⚡ Cache Caffeine — Optimisation performance

Les données d'engagement BNA/BCT sont coûteuses à récupérer. Le cache évite de recharger les mêmes données pendant 24h.

// Configuration dans application.properties spring.cache.caffeine.spec=maximumSize=500,expireAfterWrite=24h // Utilisation dans le service @Cacheable("engagementBNA") // ← résultat mis en cache public List<EngagementBNADTO> getEngagements(String numSeq) { // Appelé 1 fois, puis depuis le cache return repo.findByNumSeqPers(numSeq); }
Caches configurés : engagementBNA, engagementBCT, historiqueClasseBNA, historiqueClasseBCT, historiqueRetourClasseBct, montantTerme

🔄 Pattern DTO — Pourquoi ne pas envoyer les entités directement ?

Les entités JPA contiennent des informations sensibles et des relations complexes. Le DTO expose seulement ce dont Angular a besoin.

// Entité (NE PAS envoyer au frontend) class Caneva { Long id; // Relations qui causent des boucles JSON infinis ! @OneToMany List<Credit> credits; // Données internes qu'on ne veut pas exposer String motDePasseInterne; } // DTO (ce qu'Angular reçoit — simple et sûr) class CanevaDto { Long id; String clientNom; // calculé Integer nbCredits; // calculé String statut; // seulement le statut // Pas de relations complexes, pas de données sensibles }
Conversion Entity ↔ DTO dans le Service Java :
// Dans CanevaServiceImpl.java private CanevaDto convertToDto(Caneva entity) { CanevaDto dto = new CanevaDto(); dto.setId(entity.getId()); dto.setStatut(entity.getStade().name()); return dto; } // Ou avec ModelMapper (automatique) — MapperConfig.java CanevaDto dto = modelMapper.map(entity, CanevaDto.class); // stratégie STRICT + skipNull activés

🔐 Token JWT — Structure

Un JWT (JSON Web Token) contient 3 parties séparées par des points :

// Structure : Header.Payload.Signature eyJhbGciOiJIUzI1NiJ9 ← Header (algorithme) .eyJ1c2VyIjoiYWdlbnQiLCJleHAiOjE3..} ← Payload (données) .SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV ← Signature (vérification) // Payload contient (décodable sur jwt.io) : { "sub": "12345", // matricule agent "exp": 1748000000, // expiration (1 heure) "iat": 1747996400, // issued at "roles": ["AGENT", "..."] // rôles }

🛡️ Interception HTTP — Injection automatique du JWT

L'intercepteur Angular ajoute automatiquement le token JWT à chaque requête vers le backend.

// auth.interceptor.ts — injecte le JWT automatiquement intercept(req: HttpRequest<any>, next: HttpHandler) { const token = sessionStorage.getItem('access_token'); if (token) { req = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }); } return next.handle(req); }

Patterns de conception utilisés

Un design pattern est une solution réutilisable à un problème récurrent. Ce projet en utilise plusieurs. Les connaître te aide à comprendre pourquoi le code est organisé comme il est.
🏛️ Pattern Repository
Problème résolu : Séparer la logique d'accès aux données du reste du code.
Comment : Une interface Repository par entité. Spring génère le SQL automatiquement.
Exemple : CanevaRepository.java étend JpaRepository. Tu appelles findAll() sans écrire de SQL.
⚙️ Pattern Service (Façade)
Problème résolu : Cacher la complexité de la logique métier derrière une interface simple.
Comment : Interface + Implémentation (ICanevasService → CanevaServiceImpl).
Exemple : Le Controller appelle service.findAll() sans savoir comment c'est implémenté.
📦 Pattern DTO (Data Transfer Object)
Problème résolu : Ne pas exposer les entités JPA directement à l'extérieur.
Comment : Classes simples (sans annotations JPA) pour transporter les données.
Exemple : CanevaDto.java — Angular reçoit seulement les données nécessaires.
💉 Injection de dépendances (IoC)
Problème résolu : Éviter de créer manuellement les objets (new).
Comment : @Autowired en Java, injection dans le constructeur Angular.
Exemple : Le Controller reçoit son Service automatiquement de Spring. Le composant reçoit son Service automatiquement d'Angular.
🔍 Pattern Observer (RxJS)
Problème résolu : Réagir à des événements asynchrones (réponses HTTP).
Comment : Les Services Angular retournent des Observable. Les composants s'abonnent (subscribe()).
Exemple : canevasService.getAll().subscribe(data => this.canevas = data)
🗂️ Pattern Module (Angular)
Problème résolu : Organiser une grande application en blocs indépendants.
Comment : AppModule → LayoutModule → PagesModule → CanvasAgricoleModule (lazy-loaded).
Exemple : Le module Canvas n'est chargé que si l'utilisateur navigue vers /pages/canvas-agricole.
🔒 Pattern Intercepteur (Angular)
Problème résolu : Ajouter du comportement à toutes les requêtes HTTP sans modifier chaque service.
Comment : L'intercepteur auth.interceptor.ts injecte le JWT dans chaque requête.
Exemple : Tu n'as pas à penser au JWT dans chaque service — l'intercepteur le gère automatiquement.
🧩 Pattern Embeddable (JPA)
Problème résolu : Réutiliser un groupe de colonnes dans plusieurs tables sans créer une table séparée.
Comment : @Embeddable sur ConditionFinancement.java. Ses 13 champs sont inclus directement dans credit_investissement et credit_achat_terrain avec des préfixes de colonnes.
Exemple : c_f_nature, c_f_produit, c_f_duree... — pas de jointure nécessaire.

Conception de la base de données

🔵 Dual DataSource — Pourquoi deux bases de données ?

L'application est configurée avec deux connexions Oracle distinctes grâce à la classe DataSourceConfig.java.

// DataSourceConfig.java @Bean @Primary @ConfigurationProperties("spring.datasource.primary") public DataSource primaryDataSource() { ... } @Bean @ConfigurationProperties("spring.datasource.secondary") public DataSource secondaryDataSource() { ... } // Aussi deux JdbcClient pour les requêtes natives @Bean @Primary public JdbcClient primaryJdbcClient(...) { ... } @Bean public JdbcClient secondaryJdbcClient(...) { ... }
DatasourceURLUsage Primaire @Primary10.1.9.214:1561
SAEB.bna.tnDonnées métier principales (canevas, crédits, garanties…) Secondaire10.1.224.10:1541
bnaprodDonnées BNA existantes (engagements, clients, barèmes…)
@Primary signifie que quand Spring ne sait pas quelle datasource utiliser, il prend la primaire. La secondaire est utilisée explicitement avec @Qualifier("secondaryDataSource").

Flux complet — De l'interface à la base de données

Exemple : Créer un nouveau canevas agricole

1
🖥️ Composant Angular — add-canevas.component.ts
L'agent remplit le formulaire et clique "Créer". Le composant appelle this.canevasService.create(this.formData).
↓
2
⚡ Intercepteur HTTP — auth.interceptor.ts
Avant d'envoyer la requête, l'intercepteur ajoute automatiquement le JWT : Authorization: Bearer eyJhbG...
↓
3
⚡ Service Angular — canevas.service.ts
Envoie POST http://localhost:8081/api/canevas/canevas avec les données JSON en body.
↓ réseau HTTP
4
🔐 Spring Security — Filtre JWT
Valide le token JWT. Si invalide → répond 401 Unauthorized. Si valide → laisse passer la requête.
↓
5
🔌 Controller — CanevaController.java
Reçoit @PostMapping → CanevaDto dto. Valide les données. Appelle canevaService.create(dto).
↓
6
⚙️ Service — CanevaServiceImpl.java
Convertit DTO → Entity (convertToEntity). Applique les règles métier (date de création, statut initial). Appelle canevaRepository.save(entity).
↓
7
📦 Repository — CanevaRepository.java
Hibernate génère : INSERT INTO CANEVAS_AGRICOLE (num_seqpers, cod_strc_dem, stade, ...) VALUES (?, ?, ?, ...)
↓ JDBC / HikariCP
8
🗄️ Oracle Database — CANEVAS_AGRICOLE
La ligne est insérée. Oracle génère l'ID (IDENTITY). La transaction est commitée.
↑ Retour dans l'autre sens
9
🖥️ Angular reçoit la réponse
Le service reçoit le CanevaDto créé (avec son nouvel ID). Le composant est notifié via .subscribe(). L'interface se met à jour avec this.canevas.push(result). Un message de succès s'affiche (PrimeNG Toast).
