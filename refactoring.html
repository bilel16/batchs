R5 — Remplacer e.printStackTrace() par @Slf4j

🔴 Critique
printStackTrace() ne logge PAS en production — erreurs silencieuses
Tous les services du backend
Pourquoi c'est critique : En production avec un gestionnaire de logs (comme ELK ou Kibana), e.printStackTrace() écrit sur System.err qui n'est pas capturé. Les erreurs disparaissent sans laisser de trace dans les logs.

R9 — Memory leaks Angular : Observables non désabonnés

🔵 Moyenne
subscribe() sans cleanup dans les composants Angular
Tous les composants qui utilisent .subscribe() sans ngOnDestroy
Symptôme visible : Après navigation entre plusieurs pages, l'application devient lente. Chaque page visitée laisse des souscriptions actives en mémoire qui continuent à écouter et déclencher des mises à jour sur des composants détruits.
❌ Avant — Subscribe sans cleanup
// exploitation.component.ts — pattern dangereux export class ExploitationComponent { ngOnInit() { // ← PROBLÈME : souscription jamais annulée ! this.exploitationService .getCreditInv(id) .subscribe(data => { this.credits = data; }); this.schemaCreditService .getSchemaCredits2(ns, nc) .subscribe(schemas => { this.schemas = schemas; // Si composant détruit pendant chargement // → mise à jour d'un composant mort → erreur }); } // Pas de ngOnDestroy → mémoire jamais libérée }
✅ Après — takeUntilDestroyed (Angular 16+)
// Solution moderne Angular 16+ — une seule ligne import { takeUntilDestroyed } from '@angular/core/rxjs-interop'; import { DestroyRef, inject } from '@angular/core'; export class ExploitationComponent { // Injecter DestroyRef — Angular gère le cleanup auto private destroyRef = inject(DestroyRef); ngOnInit() { this.exploitationService .getCreditInv(id) .pipe(takeUntilDestroyed(this.destroyRef)) ← annulé auto .subscribe(data => this.credits = data); // Ou utiliser l'AsyncPipe dans le template // (zéro subscription manuelle nécessaire) credits$ = this.exploitationService.getCreditInv(id); // Template : *ngFor="let c of credits$ | async" } // Pas besoin de ngOnDestroy ! }
Tous les composants Angular Effort : 3h (chercher/remplacer) Application stable, pas de ralentissement Risque : Nul
