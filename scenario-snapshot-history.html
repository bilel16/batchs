Visibilité par Rôle (AGC / DR / DC)

🔐
La règle est pyramidale et cumulative : chaque niveau voit ses propres données plus celles des niveaux inférieurs. La donnée identifiant de quel niveau provient un log/snapshot est le champ fromStructure (pour les logs) et structureCode (pour les snapshots), qui contient les codes AGC, DR, ou DC.

Matrice de visibilité

Rôle Utilisateur Code Profil Logs AGC (Agence) Logs DR (Direction Régionale) Logs DC (Direction Centrale) Contrainte supplémentaire
Agent Agence
Chargé de clientèle		 AGC ✔ Son agence uniquement ✗ ✗ Filtre sur codeStructure de l'utilisateur
Directeur d'Agence
Chef agence		 AGC ✔ Toute son agence ✗ ✗ Filtre sur codeStructure
Direction Régionale
Analyste / Directeur DR		 DR ✔ Toutes agences de sa région ✔ Sa propre DR uniquement ✗ Filtre sur structureMere pour les AGC
Direction Centrale
Analyste / Décideur DC		 DC ✔ Toutes les agences ✔ Toutes les DR ✔ DC complète Aucun filtre géographique

AGC — Logique de filtrage

L'utilisateur Agence récupère uniquement les logs et snapshots où :

  • fromStructure == user.codeStructure
  • OU toStructure == user.codeStructure
  • ET structureCode == "AGC"
GET /api/canevas/{id}/snapshots/workflow-log
Query: structureFilter=AGC&codeStructure=AGC-001

DR — Logique de filtrage

La Direction Régionale voit ses propres logs + ceux des agences sous sa tutelle :

  • Logs où structureCode == "AGC" ET structureMere == user.codeStructure
  • Logs où structureCode == "DR" ET fromStructure == user.codeStructure
GET /api/canevas/{id}/snapshots/workflow-log
Query: structureFilter=DR&codeStructure=DR-05

DC — Logique de filtrage

La Direction Centrale n'a aucun filtre géographique, elle voit l'historique complet :

  • Tous les logs et snapshots, tous niveaux confondus
  • Peut voir les commentaires confidentiels DC
GET /api/canevas/{id}/snapshots/workflow-log
Query: structureFilter=DC

Implémentation frontend recommandée — snapshot-history.component.ts

// Récupérer le profil de l'utilisateur connecté
const user = this.authService.getCurrentUser();
const typeStructure = user?.typeStructure; // "AGC" | "DR" | "DC"
const codeStructure = user?.codeStructure; // ex: "AGC-001"
const structureMere = user?.structureMere; // ex: "DR-05" (pour les AGC)

// Filtrer les logs selon le rôle
filteredLogs = computed(() => {
  const logs = this.workflowLog();
  if (typeStructure === 'AGC') {
    return logs.filter(l => l.fromStructure === codeStructure || l.toStructure === codeStructure);
  } else if (typeStructure === 'DR') {
    return logs.filter(l =>
      (l.fromStructure?.startsWith('AGC') && l.fromStructureMere === codeStructure)
      || l.fromStructure === codeStructure || l.toStructure === codeStructure
    );
  } else { // DC : aucun filtre
    return logs;
  }
});
⚠️
Le champ fromStructureMere n'existe pas encore dans CanevasWorkflowLog. Il faudra soit l'ajouter à l'entité, soit faire une jointure backend avec la table des structures pour résoudre la hiérarchie DR → AGC. Recommandation : ajouter un champ structureMere dans CanevasWorkflowLog au moment de la création du log.

Détail d'un Snapshot (clic sur l'icône 👁)

📸
Un snapshot stocke l'état complet du canvas sous forme de JSON CLOB dans la base. Lorsque l'utilisateur clique sur 👁, l'application appelle GET /api/canevas/{id}/snapshots/structure/{structureCode} (ou via snapshotId) et affiche les données dans un panneau dédié en lecture seule.

📊 Données stockées dans un snapshot

engagementBnaJson Liste engagements BNA au moment T
engagementBctJson Liste engagements BCT au moment T
classeBnaJson Historique classes BNA
donneesCreditsJson Crédits (CT / Inv / Achat Terrain)
donneesExploitationJson Sites, élevage, matériel, bâtiment
donneesAvisJson Avis/opinions (favorable/défavorable)
engagementDetailleJson Actionnaires, 1er responsable, vendeurs

🗂 Onglets du panneau de détail

Le panneau détail reprend la structure du composant SnapshotDetailDto et affiche chaque section dans un onglet dédié.

  • Onglet 1 — Engagements Relation (BNA + BCT)
  • Onglet 2 — Actionnaires
  • Onglet 3 — 1er Responsable
  • Onglet 4 — Vendeurs
  • Onglet 5 — Crédits sollicités
  • Onglet 6 — Exploitation (sites)
  • Onglet 7 — Avis & Garanties

Endpoints API utilisés

Backend — CanevasSnapshotController

// Récupérer l'historique complet des snapshots d'un canvas
GET /api/canevas/{id}/snapshots
Roles: AGC, DR, DC    → List<SnapshotSummaryDto>

// Récupérer le dernier snapshot d'une structure donnée
GET /api/canevas/{id}/snapshots/structure/{structureCode}
Roles: AGC, DR, DC    → Optional<SnapshotDetailDto>

// Récupérer le log workflow (toutes les transitions)
GET /api/canevas/{id}/snapshots/workflow-log
Roles: AGC, DR, DC    → List<CanevasWorkflowLog>

// Valider et transmettre (crée snapshot + log)
POST /api/canevas/{id}/valider
Body: ValidationRequestDto { fromStructureCode, toStructureCode, matricule, observations, avisValue }
→ SnapshotResponseDto { snapshotId, versionNumber, structureCode }

// Refouler (crée snapshot avec statut CORRIGE_DONNEE + log)
POST /api/canevas/{id}/refouler
Body: RefoulementRequestDto { fromStructureCode, toStructureCode, matricule, motif }
→ SnapshotResponseDto

Frontend — SnapshotService (Angular)

7 Idées Innovantes pour le Système d'Historique

💡
Ces idées vont au-delà du minimum fonctionnel pour transformer l'historique en un outil de pilotage bancaire, de détection des anomalies, et d'intelligence métier. Chaque idée est réalisable avec la stack existante (Angular 17 + Spring Boot 3.2 + Oracle).
⏱

Timeline Interactive Visuelle

Remplacer le tableau plat par une timeline verticale animée avec des nœuds cliquables représentant chaque action. Chaque nœud affiche : l'acteur, la durée depuis l'action précédente, et un aperçu rapide (tooltip) du snapshot. Les refoulements sont affichés en rouge avec une flèche vers le haut pour visualiser le "rebond".

  • Librairie : ngx-timeline ou PrimeNG Timeline
  • Animation : Angular Animations (slide-in par ordre chronologique)
  • Aucun backend supplémentaire requis
🎨 UX/UI Effort: faible
⚖

Comparateur de Snapshots (Diff View)

Bouton "Comparer" entre deux snapshots qui affiche un diff côte à côte des données financières. Les valeurs qui ont changé sont surlignées en vert (augmentation) ou en rouge (diminution). Idéal pour la DR qui veut voir ce que l'AGC a modifié après un refoulement.

  • Comparaison JSON deep-diff côté frontend
  • Librairie : deep-diff (npm)
  • Sélection de deux versions via checkboxes dans la liste
🔍 Audit Effort: moyen
⏰

Indicateur de Délai de Traitement (SLA)

Calculer et afficher la durée passée à chaque étape du workflow. Si un canvas reste plus de X jours sans action, un badge d'alerte apparaît dans la liste. La DR peut ainsi identifier les dossiers "en retard" dans ses agences.

  • Calcul : performedAt[n+1] - performedAt[n]
  • Seuils configurables par structure (ex: AGC = 5 jours, DR = 10 jours)
  • Badge rouge si dépassé, orange si proche du seuil
  • Rapport exportable : "Canvas en retard par agence"
📊 Pilotage Effort: moyen
🔒

Mode Audit DC — Vue "Rayons X"

Pour la Direction Centrale uniquement, activer un mode audit spécial qui révèle les métadonnées cachées : IP de connexion, device, durée de session lors de chaque action. Ce mode génère un rapport d'audit PDF signé horodaté, qui peut servir de preuve légale en cas de litige.

  • Stocker IP + user-agent dans CanevasWorkflowLog
  • Export PDF via jsPDF (déjà présent dans le projet)
  • Signature numérique (hash SHA-256 du rapport)
  • Accès conditionné au profil DC uniquement
🔐 Sécurité Effort: élevé
🔁

Restauration de Snapshot ("Retour dans le temps")

Permettre à un utilisateur autorisé de restaurer l'état d'un snapshot comme base de travail. Utile lorsqu'une modification récente est erronée et qu'il faut repartir d'une version antérieure. La restauration crée automatiquement un nouveau snapshot de type "RESTORE" avec traçabilité complète.

  • Endpoint : POST /api/canevas/{id}/snapshots/{snapshotId}/restore
  • Accessible uniquement aux profils DR/DC avec confirmation explicite
  • Journal d'audit obligatoire avec motif de restauration
  • Le canvas restauré passe en statut CORRIGE_DONNEE
⚡ Résilience Effort: élevé
📊

Tableau de Bord "Velocity" par Agence

Un dashboard accessible à la DR et DC qui montre, pour chaque agence sous tutelle, un graphique de vélocité : nombre de canvas validés / refoulés par semaine, temps moyen de traitement, taux de refoulement. Aide la DR à identifier les agences qui ont besoin de formation ou de ressources.

  • Endpoint : GET /api/analytics/agence/{code}/velocity
  • Graphiques : PrimeNG Charts (déjà dans le projet)
  • Données agrégées depuis CanevasWorkflowLog
  • Export Excel/CSV des métriques
📈 Analytics Effort: élevé
💬

Commentaires Filés par Snapshot ("Thread")

Transformer les commentaires one-shot actuels en un fil de discussion structuré attaché à chaque snapshot. Les acteurs (AGC, DR, DC) peuvent répondre aux commentaires précédents, créant un historique conversationnel du dossier. Chaque message est horodaté et signé par le matricule.

  • Nouvelle entité : SnapshotComment { id, snapshotId, parentId, body, matricule, createdAt }
  • Endpoint : POST /api/canevas/{id}/snapshots/{snapshotId}/comments
  • Affichage : PrimeNG Timeline ou composant thread custom
  • Notifications push lors d'une réponse (optionnel)
💬 Collaboration Effort: moyen
