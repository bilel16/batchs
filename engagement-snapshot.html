Partie 1 — Comment les engagements fonctionnent aujourd'hui

Les engagements représentent toutes les expositions bancaires d'un client : crédits accordés, utilisés, impayés, classe de risque BCT/BNA, etc. Ce sont des données lues depuis Oracle SAEB (datasource secondaire), jamais stockées dans notre base métier. Elles sont affichées en lecture seule dans le canevas.

5 onglets dans l'interface

  • Onglet 0 — RELATION : le client lui-même
  • Onglet 1 — ACTIONNAIRE : ses actionnaires
  • Onglet 2 — 1er RESPONSABLE : le dirigeant
  • Onglet 3 — GROUPE : son groupe d'entreprises
  • Onglet 4 — VENDEUR : vendeurs de terrain

8 types d'engagement BNA

  • FCDP — Facilités de caisse & découverts
  • CME — Crédits moyen terme export
  • EPS — Engagements par signature
  • ESC — Escompte commercial
  • INV — Investissement (CMT/CLT)
  • BPN — CCI / billets à ordre
  • AGR — Crédits agricoles SAEBAGR
  • SBE — Encours total SBE

3 types d'historique

  • Classe BNA — Historique 3 ans (cod_solv_solv + @CARTHAGO)
  • Classe BCT — hist_class_bna sur 3 ans
  • Retour classe BCT — bi_user.retour_classe_bct (mois/an, NB déclarants, encours)

Les requêtes SQL — Fichier de configuration

Toutes les requêtes sont externalisées dans resources/sql/engagements/engagement-queries.properties et chargées par queryconfig/QueryConfig.java au démarrage du serveur.

Requête principale BNA — Type AGR (Agricole)

C'est la plus importante pour notre contexte. Elle interroge SAEBAGR via database link.

-- getEngAGR dans engagement-queries.properties -- Tables : SAEBAGR.credit_agri (via @link) + COMM_DEBAGR SELECT ca.num_cpt_crd_agri -- numéro compte crédit ,ca.cod_detat_crdagr -- état crédit (1=accordé, E=en cours, N=nouveau) ,ca.mnt_crd_agri -- montant autorisé ,ca.mnt_enc_agri -- encours ,ca.mnt_imp_agri -- impayés ,comm.mnt_commission -- commission (codes 203, 83) ,ca.dat_ech_dern_crdagri -- date dernière échéance FROM SAEBAGR.credit_agri ca LEFT JOIN COMM_DEBAGR comm ON ca.num_cpt = comm.num_cpt AND comm.cod_comm IN (203, 83) WHERE ca.num_pers_agri = :numSeqPers AND ca.detat_crdagr IN ('1','E','N')

Requête historique Retour Classe BCT

Utilisée dans historical-bct-class.component.ts pour afficher l'évolution de la classe sur 3 ans.

-- getHistoriqueRetourClasseBctBNA -- Table : bi_user.retour_classe_bct (datasource secondaire) SELECT annee, mois, classe_secteur, -- classe dans le secteur bancaire classe_declarant, -- classe chez la BNA nbr_declarant, -- nombre de banques déclarantes eng_secteur, -- encours total secteur eng_declarant -- encours BNA FROM bi_user.retour_classe_bct WHERE num_seqpers = :numSeqPers AND annee BETWEEN (EXTRACT(YEAR FROM SYSDATE) - 2) AND EXTRACT(YEAR FROM SYSDATE) ORDER BY annee DESC, mois DESC

Partie 2 — Implémenter le Snapshot d'Engagement

Objectif du snapshot (basé sur le cas de test) : Quand la DR modifie un dossier et transmet à la DC, le système doit figer une photo des données d'engagement à cet instant précis. La DR ne peut plus modifier, mais peut consulter la photo qu'elle avait envoyée. La DC voit les données de la DR, pas celles de l'agence.

Pourquoi un snapshot d'engagement spécifiquement ?

Les engagements changent dans Oracle SAEB en temps réel. Si la DR transmet un dossier aujourd'hui avec "encours = 120 000 DT" et que demain la DC consulte, Oracle pourrait afficher "encours = 145 000 DT" (si un nouveau crédit a été accordé).

Le snapshot garantit que chaque structure voit exactement les engagements qui existaient au moment de sa décision.

Ce que le cas de test montre :

Snapshot v1 (AGC) → engagements au 10/05
Snapshot v2 (DR) → engagements au 12/05
Snapshot v3 (DC) → engagements au 15/05

Chaque structure peut relire ses propres données d'engagement même après que les données Oracle ont changé.

Schéma de base de données — Tables à créer

Table 1 — CANEVAS_STRUCTURE_SNAPSHOT

Stocke une photo complète des données à chaque transition de structure. Les données engagement sont sérialisées en JSON dans un CLOB.

-- Script Oracle à exécuter (Flyway V5__add_snapshot.sql) CREATE TABLE CANEVAS_STRUCTURE_SNAPSHOT ( snapshot_id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, canevas_id NUMBER NOT NULL, structure_code VARCHAR2(20) NOT NULL, -- 'AGC', 'DR', 'DC' structure_label VARCHAR2(100), -- 'Agence Béja Nord' version_number NUMBER NOT NULL, -- 1, 2, 3... status_at_snapshot VARCHAR2(50), -- 'ENREGISTRE', 'EN_COURS_ETUDE' created_by VARCHAR2(100), matricule VARCHAR2(20), created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, observations CLOB, -- Données engagement sérialisées en JSON engagement_bna_json CLOB, -- snapshot EngagementDTO sérialisé engagement_bct_json CLOB, -- snapshot BCT sérialisé classe_bna_json CLOB, -- historique classe BNA classe_bct_json CLOB, -- historique classe BCT classe_retour_json CLOB, -- retour classe BCT -- Données métier (pour comparaison inter-structures) donnees_credits_json CLOB, donnees_exploitation_json CLOB, donnees_garanties_json CLOB, donnees_avis_json CLOB, CONSTRAINT fk_snapshot_canevas FOREIGN KEY (canevas_id) REFERENCES CANEVAS_AGRICOLE(id), CONSTRAINT uq_snapshot_version UNIQUE (canevas_id, structure_code, version_number) ); -- Index pour les requêtes fréquentes CREATE INDEX idx_snapshot_canevas ON CANEVAS_STRUCTURE_SNAPSHOT(canevas_id); CREATE INDEX idx_snapshot_structure ON CANEVAS_STRUCTURE_SNAPSHOT(canevas_id, structure_code);

Table 2 — CANEVAS_WORKFLOW_LOG

Trace chaque transition (VALIDER, REFOULER, PRE_VALIDER, ANNULER) avec lien vers le snapshot.

CREATE TABLE CANEVAS_WORKFLOW_LOG ( log_id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, canevas_id NUMBER NOT NULL, from_structure VARCHAR2(20), -- structure émettrice to_structure VARCHAR2(20), -- structure réceptrice action VARCHAR2(30) NOT NULL, -- VALIDER/REFOULER/PRE_VALIDER/ANNULER snapshot_version NUMBER, -- lien vers version du snapshot snapshot_id NUMBER, -- FK vers snapshot comments CLOB, performed_by VARCHAR2(100), performed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_wflog_canevas FOREIGN KEY (canevas_id) REFERENCES CANEVAS_AGRICOLE(id), CONSTRAINT fk_wflog_snapshot FOREIGN KEY (snapshot_id) REFERENCES CANEVAS_STRUCTURE_SNAPSHOT(snapshot_id), CONSTRAINT chk_action CHECK (action IN ('VALIDER','PRE_VALIDER','REFOULER','ANNULER','CORRIGER')) ); CREATE INDEX idx_wflog_canevas ON CANEVAS_WORKFLOW_LOG(canevas_id); -- Ajouter colonnes sur la table principale ALTER TABLE CANEVAS_AGRICOLE ADD ( current_version NUMBER, -- numéro du snapshot courant current_structure VARCHAR2(20), -- structure détenant le dossier last_snapshot_id NUMBER -- FK dernier snapshot );

Scénario réel — Ce qui se passe en base de données

Basé exactement sur le cas de test : client Mohamed Ben Ali, canevas 5001, Agence Béja Nord → DR Nord-Ouest → DC.

Étape 1 — Sonia Mejri (chef agence) valide → POST /api/canevas/5001/valider

Le système appelle snapshotService.createSnapshot(5001, "AGC", "Agence Béja Nord", ...) qui :

  1. Charge les engagements réels depuis Oracle SAEB via engagementService.getListeEngagementClient("07845612")
  2. Sérialise la liste des 8 types BNA en JSON → engagementBnaJson
  3. Sérialise BCT, classeBNA, classeRetour → CLOBs séparés
