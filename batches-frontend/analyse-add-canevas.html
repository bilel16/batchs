1. Vue d'ensemble de l'arborescence

AddCanevasComponent est l'écran principal du dossier "Canevas Agricole". Il combine :

  • Une barre de navigation p-menubar qui ouvre des p-dialog (fiches annexes)
  • Un p-stepper (assistant en 4 étapes) qui charge le contenu principal du dossier
add-canevas.component (racine) │ ├── <app-agent-canevas> → bandeau "agent en charge" (toujours visible) │ ├── <p-dialog> (ouvert via p-menubar) │ ├── <app-fiche-signalitique-2> ─ si selectedLabel === 'FICHE SIGNALITIQUE' │ ├── <app-engagements> ─ si selectedLabel === 'ENGAGEMENT' │ ├── <app-analyse-financier> ─ si selectedLabel === 'Analyse Financiers' │ ├── <app-condition-banque> ─ si selectedLabel === 'Conditions Banques' │ └── <app-garanties> ─ si selectedLabel === 'GARANTIES' │ └── <p-stepper> (4 panels horizontaux) ├── Étape 0 : <app-credit-sollicite [client] [mode]> ├── Étape 1 : <app-garanties-proposees> ├── Étape 2 : <app-exploitation [tabIndex]> └── Étape 3 : <app-avis [tabIndex]>

Tous les composants reposent sur des services partagés à base de signals (CanevasAgrService, EngagementService, GarantieService, BilanService, AnalyseFinanciereService, CreditSolliciteService, UserService) — c'est le mécanisme central de communication entre composants frères, à la place de @Input/@Output classiques.

3.3 — CSS (add-canevas.component.css)

Problèmes principaux :
  • .scrollbar-tracking-menu { position: fixed; right:20px; } + binding [style.top.px]="menuTopPosition + 70" → comme menuTopPosition ne change jamais, le menu reste figé à 70px du haut du viewport, sans lien avec la topbar (64px) ni avec le défilement.
  • :host ::ng-deep .p-stepper-nav { position: sticky; top: 130px; } → valeur magique 130px qui ne correspond à aucune variable du layout (topbar 64px + marge interne ?). Si la topbar change de hauteur (ex: passage en mode responsive où elle devient auto), ce top devient faux.
  • #status-header { position: sticky; top: 120px; } → règle définie mais l'id status-header n'existe nulle part dans le HTML (commentaire ligne 1 du HTML montre qu'il a été retiré) → CSS mort.
  • Couleurs codées en dur : #4caf50, #42A5F5, #b30fccff, #FFA726, #e20e0eff au lieu de variables PrimeNG (var(--primary-color), var(--green-500), etc.)
  • Usage massif de ::ng-deep (12 occurrences) pour personnaliser p-menubar et p-stepper → casse l'encapsulation des styles, risque de collision avec d'autres pages utilisant les mêmes composants PrimeNG.

4. Astuces & bonnes pratiques pour un développeur débutant

Cette section explique les patterns réutilisables déjà présents dans le code, pour qu'un débutant comprenne le "pourquoi" avant de les copier ailleurs.

4.1 — Une seule p-dialog pour plusieurs contenus (pattern "dialog factorisée")

Plutôt que de créer 5 fenêtres modales différentes, on garde une seule <p-dialog> et on affiche le bon composant à l'intérieur avec *ngIf="selectedLabel === '...'". La variable header change le titre dynamiquement. 
<p-dialog [(visible)]="visible" header="{{header}}">
  <app-engagements *ngIf="selectedLabel === 'ENGAGEMENT'"></app-engagements>
  <app-garanties *ngIf="selectedLabel === 'GARANTIES'"></app-garanties>
</p-dialog>

Avantage : un seul état visible à gérer. Limite : Angular détruit/recrée le composant à chaque changement de selectedLabel — donc tout état non sauvegardé dans un service est perdu. C'est pour ça que showDialog() appelle systématiquement un service (setNumSeqPers, etc.) pour que le composant recharge ses données à sa création.

4.2 — ng-template pTemplate="item" : personnaliser le rendu d'un menu PrimeNG

PrimeNG fournit un rendu par défaut pour p-menubar, mais on peut le remplacer entièrement avec un template nommé. Ici chaque entrée du menu devient un vrai p-button cliquable. 
<ng-template pTemplate="item" let-item>
  <p-button (onClick)="showDialog(item.label)" [icon]="item.icon">
    {{item.label}}
  </p-button>
</ng-template>

4.3 — p-stepper : callbacks prevCallback / nextCallback + index

Chaque ng-template pTemplate="content" d'un p-stepperPanel reçoit automatiquement 3 variables fournies par PrimeNG : prevCallback, nextCallback (fonctions à appeler pour naviguer) et index (numéro de l'étape, utile pour stepContentColors[index]). 
<ng-template pTemplate="content" let-nextCallback="nextCallback" let-index="index">
  <div [ngStyle]="{'background-color': stepContentColors[index]}">
    <app-credit-sollicite [client]="client" [mode]="mode"></app-credit-sollicite>
  </div>
  <p-button label="Next" (onClick)="nextCallback.emit()" />
</ng-template>

L'événement (activeStepChange)="onStepChange($event)" sur <p-stepper> permet d'exécuter du code au moment du changement d'étape (ici : précharger les données de l'étape suivante via les services).

4.4 — Signals & effect() : communication entre composants sans @Input/@Output

Au lieu de faire remonter/redescendre des données via @Input/@Output sur plusieurs niveaux, un service injecté en providedIn:'root' expose des signal(). N'importe quel composant peut lire ou écrire cette valeur, et effect() réagit automatiquement aux changements. 
// Dans le service
activeTabCanva = signal(0);
updateActiveTab(tab: number, ...) { this.activeTabCanva.set(tab); }

// Dans le composant
constructor(public canevasService: CanevasAgrService) {
  effect(() => {
    this.tabIndex = this.canevasService.activeTabCanva(); // se relance à chaque .set()
  });
}

Astuce débutant : effect() doit être appelé dans un contexte d'injection (constructeur, ou via injector), jamais dans une méthode comme ngOnInit sans précaution.

4.5 — fieldset [disabled]="!permission()" : verrouiller un formulaire selon le rôle utilisateur

userService.boolDisplayRubrique() est un signal booléen basé sur les droits de l'utilisateur connecté. En l'attachant à l'attribut natif disabled d'un <fieldset>, tous les champs et boutons à l'intérieur deviennent automatiquement non-éditables — pas besoin de désactiver chaque champ un par un. 
<fieldset [disabled]="!userService.boolDisplayRubrique()">
  <app-credit-sollicite ... ></app-credit-sollicite>
</fieldset>

4.6 — ConfirmationService + MessageService (Toast) : confirmation avant action destructive

this.confirmationService.confirm({
  message: 'Voulez vous sauvegarder les modifications effectuées',
  header: 'Confirmation',
  accept: () => { this.saveCanevas(); this.messagingService.add({severity:'info', summary:'Confirmed', detail:'Enregistrer avec succée'}); },
  reject: () => { this.messagingService.add({severity:'error', summary:'Annuler', detail:'Sauvegarde Annulé'}); }
});

Le <p-toast key="ct"> dans le template doit avoir la même key que celle utilisée dans messagingService.add({key:'ct', ...}) si on veut cibler un toast précis (ici la key n'est pas passée dans add(), donc le toast par défaut sera utilisé — à harmoniser).

6. Compatibilité avec la Topbar et la Sidebar existantes

6.1 — Le constat

  • Le menu flottant .scrollbar-tracking-menu est en position: fixed; right: 20px — il ignore donc complètement la sidebar (285px) et reste ancré à droite du viewport. Sur petit écran (sidebar repliée en mode mobile), il peut chevaucher le contenu.
  • Les top: 120px / 130px ne correspondent à aucune variable du layout global (topbar = 4rem, padding du container = 4.5rem). Ce sont des valeurs "qui marchent par hasard" sur l'écran de test actuel.
  • :host ::ng-deep .p-stepper-nav { position: sticky; top: 130px; } entre potentiellement en conflit avec le menu fixed du dessus (lui-même à top: 70px) : zone de chevauchement possible entre 70px et 130px+hauteur du menubar.
  • Le p-panel englobant (CANEVAS AGRICOLE) a [style]="{'color':'red'}" codé en dur — incohérent avec la charte (vert #4ade80 de la topbar).

6.2 — Le principe de correction

Le .layout-main-container applique déjà padding-top: 4.5rem (espace topbar) et margin-left: 300px (espace sidebar) sur desktop. Le contenu de add-canevas est donc déjà "dans" la zone libre.

→ Il ne faut plus utiliser position: fixed pour le menu, mais position: sticky relatif à son propre conteneur (qui est déjà décalé correctement). Avec sticky, l'élément reste dans le flux normal (respecte la sidebar) mais se "colle" en haut de la zone visible lors du scroll.

6.3 — Variables CSS proposées (à ajouter dans _variables.scss ou un fichier global)

:root {
  --app-topbar-height: 4rem;     /* = 64px, doit matcher .layout-topbar */
  --app-sidebar-width: 285px;    /* = .layout-sidebar */
  --app-sticky-gap: 0.5rem;      /* petit espace de respiration */
}

6.4 — CSS corrigé pour add-canevas.component.css

/* AVANT (problématique) */
.scrollbar-tracking-menu {
  position: fixed;
  right: 20px;
  transition: all 0.3s ease;
}
:host ::ng-deep .p-stepper-nav {
  position: sticky;
  top: 130px; /* valeur magique */
}

/* APRÈS (compatible topbar/sidebar) */
.scrollbar-tracking-menu {
  position: sticky;
  top: var(--app-topbar-height);   /* colle juste sous la topbar, dans le flux */
  z-index: 999;
  margin-left: auto;               /* aligne à droite dans son conteneur */
  width: fit-content;
}

:host ::ng-deep .p-stepper-nav {
  position: sticky;
  /* sous le menubar : topbar + hauteur réelle du menubar (mesurée ~3.5rem) */
  top: calc(var(--app-topbar-height) + 3.5rem);
  z-index: 998;
}

/* Supprimer entièrement la règle #status-header (CSS mort, élément inexistant) */

<!-- APRÈS : le top est désormais géré entièrement en CSS via var(--app-topbar-height) -->
<div class="scrollbar-tracking-menu">

7. Recommandations de design détaillées

🎨 Harmonisation des couleurs

Remplacer les couleurs codées en dur par les variables PrimeNG / charte BNA déjà définies (vert #4ade80 de la topbar, --primary-color du thème PrimeNG) :

/* AVANT */
background-color: #4caf50;
color: green;

/* APRÈS */
background-color: var(--primary-color);
color: var(--green-600);

🧩 Réduire les ::ng-deep

Centraliser les overrides PrimeNG répétés (couleurs de p-stepper, p-fieldset, p-datatable) dans un seul fichier de thème global (src/assets/layout/styles/theme/_canevas-overrides.scss) importé une fois, plutôt que de dupliquer ::ng-deep dans chaque composant.

📐 Largeurs responsives des dialogs

Remplacer les largeurs fixes (80rem, 380px) par des valeurs relatives bornées :

[style]="{ width: '90vw', maxWidth: '1200px' }"
[breakpoints]="{ '1199px': '95vw', '575px': '98vw' }"

Important quand la sidebar (285px) réduit l'espace disponible sur écrans < 1366px.

🧹 Nettoyage du code mort

  • Supprimer menuTopPosition + import HostListener
  • Supprimer la règle #status-header
  • Décommenter ou supprimer définitivement le tableau value commenté (lignes 53-56 du .ts)

🔌 Centraliser les appels HTTP

Déplacer les appels http.get('http://localhost:8081/...') trouvés dans fiche-signalitique-2.component.ts vers un service dédié, en utilisant environment.apiUrl.

🔁 Uniformiser Signals vs @Input/@Output

app-analyse-financier utilise encore @Output alors que la majorité des autres composants utilisent des signal()/computed() partagés via service. À terme, migrer vers le pattern signal pour cohérence (plus simple à débugger, pas de souscriptions à gérer).
