Guide Développeur — PGCANVAS

Ce guide explique le rôle exact de chaque fichier du projet Angular. Conçu pour un développeur débutant qui veut comprendre la structure et faire ses premières modifications en confiance.

Architecture Globale

PGCANVAS est une application Angular 17 avec un backend Spring Boot. Voici comment les grandes parties s'articulent.

🖥️
Frontend Angular 17
Dossier frontend-app1/
Interface utilisateur, formulaires, navigation, affichage des données.
⚙️
Backend Spring Boot
Dossier backend-saeb/
API REST, base de données Oracle, logique métier, authentification.
🔐
Auth Server
Serveur externe sur port 7070
Gère les connexions, les tokens JWT et les profils utilisateurs.
ℹ️
Principe clé : Le frontend Angular ne parle JAMAIS directement à la base de données. Il passe toujours par les services Angular → API REST (port 8081) → Base Oracle.

Stades du Workflow — Cycle de Vie d'un Canevas

Chaque dossier (canevas) passe par des étapes précises. Le champ stade dans le modèle Caneva indique à quelle étape il se trouve.

INIT_DONNEE
Canevas créé, données initiales saisies
PEC_DONNEE
Prise en charge par le chargé de crédit (CHARGER)
VALID_DONNEE
Validé par le chef d'agence (CHAGCE)
CORRIGE_DONNEE
Renvoyé pour correction
PEC_AVIS_DEC
Prise en charge avis/décision (PROFILE3)
VALID_AVIS_DEC
Avis validé (PROFILE4)
CLOTURE
Dossier clôturé
⚠️
Règle importante : Un utilisateur ne peut voir et modifier que les canevas dont le stade correspond à son profil. C'est géré dans list.component.ts via la méthode isRowSelectable() et la config ALLOWED_STADES.

Système de Sécurité — 4 Fichiers

La sécurité est gérée par 4 fichiers qui travaillent ensemble. Il faut tous les comprendre.

🔑
auth.service.service.ts — Service de Connexion
src/app/core/services/auth.service.service.ts
SÉCURITÉ

Gère la connexion et la déconnexion de l'utilisateur. Stocke qui est connecté via des Signals Angular (état réactif).

  • login(username, password) : envoie les identifiants au serveur d'auth (port 7070), reçoit le token JWT en retour
  • getAccessToken() : retourne le token JWT stocké dans la session
  • isTokenExpired() : vérifie si le token est encore valide
  • clearStorage() : efface la session (déconnexion)
  • currentUserSignal : signal réactif qui contient l'utilisateur connecté
💾
token-storage.service.ts — Stockage de Session
src/app/core/services/token-storage.service.ts
SESSION

Gère le stockage des données de session dans le navigateur (sessionStorage + localStorage). C'est ici que le token JWT, l'utilisateur et les menus sont sauvegardés.

// Ce qui est stocké dans sessionStorage : - 'access_token' → le token JWT (clé d'accès API) - 'user' → objet utilisateur (nom, matricule, profils…) - 'menus' → menus autorisés pour cet utilisateur // Méthodes clés : saveToken(token) // stocker le token getToken() // lire le token getUser() // lire l'utilisateur getProfiles() // lire les profils [CCA, CHAGCE…] isLoggedIn() // vérifier si connecté signOut() // effacer la session
🚧
auth.guard.ts — Gardien des Routes
src/app/core/guards/auth.guard.ts
GUARD

Protège les pages de l'application. Avant d'afficher une page, Angular appelle ce fichier. S'il retourne false, l'utilisateur est redirigé vers la page de connexion.

canActivate(): boolean { // 1. Est-ce qu'il y a un token ? if (!tokenStorage.getToken()) { window.location = environment.portalLogin; // → portail BNA return false; } // 2. Est-ce que l'utilisateur existe ? if (!tokenStorage.getUser()) { return false; } // 3. Est-ce que le menu est autorisé ? // vérifie les menus stockés en session return true; // accès autorisé }
🔄
auth.interceptor.ts — Ajout Automatique du Token
src/app/core/interceptors/auth.interceptor.ts
HTTP

Intercepte TOUTES les requêtes HTTP avant qu'elles partent vers le backend et ajoute automatiquement le token JWT dans l'en-tête. Sans ça, l'API refuserait les requêtes.

// Ce que fait l'intercepteur pour chaque requête : intercept(request, next) { const token = tokenStorage.getToken(); // Ajoute le header Authorization: Bearer {token} const authReq = request.clone({ headers: request.headers.set( 'Authorization', `Bearer ${token}` ) }); // Si le serveur répond 401 (token expiré) → déconnexion return next.handle(authReq).pipe( catchError(err => { if (err.status === 401) { handle401Error(); } }) ); }
💡
Grâce à cet intercepteur, les services Angular n'ont PAS besoin d'ajouter le token manuellement dans chaque appel HTTP. C'est fait une seule fois ici.

app.menu.component — Construction du Menu Latéral
src/app/_components/layout/app.menu.component.ts
MENU DYNAMIQUE

C'est ce fichier qui décide quels menus l'utilisateur voit. Le menu est construit dynamiquement selon les profils de l'utilisateur. Deux utilisateurs avec des profils différents voient des menus différents.

  • Profil PROFILE3 → voit "PEC AVIS CANEVAS AGRICOLE"
  • Profil PROFILE4 → voit "VALIDATION AVIS DÉCISION"
  • Profil PROFILE5 → voit "AFFECTATION CANEVAS"
// Exemple d'un item de menu dans buildMenu() { label: 'PEC CANEVAS AGRICOLE', icon: 'pi pi-fw pi-file', routerLink: ['/pages/agricole/searshClient'], visible: profiles.includes('CCA') // visible si profil CCA }
📌 Ajouter un item de menu ? Ouvrir app.menu.component.ts, trouver la méthode buildMenu(), et ajouter un objet { label, icon, routerLink, visible } dans le bon tableau.

avis — Formulaire d'Avis et Décision
src/app/_components/pages/canvas.agricole/avis/
PAGE COMPLEXE

La page de décision finale sur un dossier. Accessible selon le profil et le stade du canevas. Plusieurs "sous-avis" selon le type de crédit.

  • loadExistingAvis() : charge l'avis existant depuis l'API selon la hiérarchie de statut
  • saveAvis() : enregistre l'avis principal + les sous-avis (crédit court terme, investissement, achat terrain, garanties)
  • submitAction() : soumet le dossier à l'étape suivante du workflow
  • decisionFinaleCaneva() : marque le dossier comme décidé définitivement
  • updateConditionalValidators() : selon le profil, certains champs deviennent obligatoires
  • createAffectationRecords() : crée les enregistrements d'audit trail
🔷
C'est le composant le plus complexe. Il gère : les formulaires réactifs, les validators dynamiques, la navigation du workflow, les appels multi-services (AvisService, GarantieService, AffectationService), et les confirmations utilisateur.
