Sécurité

6 points
🔴 Critique
Secrets en clair dans les fichiers de configuration
application.properties · application.yml

Les mots de passe Oracle, la clé secrète JWT et les credentials LDAP sont écrits en clair dans les fichiers de configuration versionnés. C'est la vulnérabilité la plus critique du projet.

Problème actuelspring.datasource.password=motDePasse
jwt.secret=monSecretJWT123
SolutionUtiliser des variables d'environnement OS ou un vault (HashiCorp Vault, Spring Cloud Config Server avec encryption).
# application.properties — MAUVAISE pratique spring.datasource.password=saeb_password_prod # BONNE pratique — variables d'environnement spring.datasource.password=${DB_PASSWORD} spring.datasource.url=${DB_URL} jwt.secret=${JWT_SECRET}
Spring Cloud Config HashiCorp Vault Effort: Faible Impact: Maximal
🔴 Critique
Absence de HTTPS / TLS en production
Tous les services — HTTP non chiffré

Aucune configuration SSL/TLS n'est présente dans les fichiers de config. Le trafic entre le frontend Angular, les backends Spring Boot et la base Oracle circule en clair.

RisqueInterception de tokens JWT, credentials DB, données clients agricoles sensibles sur le réseau interne BNA.
SolutionConfigurer SSL sur Spring Boot (keystore PKCS12) ou placer un reverse proxy Nginx/Apache avec certificat TLS devant chaque service.
# application.properties — Activer HTTPS Spring Boot server.ssl.enabled=true server.ssl.key-store=classpath:keystore.p12 server.ssl.key-store-password=${SSL_KEYSTORE_PASSWORD} server.ssl.key-store-type=PKCS12 server.port=8443
TLS/SSLNginx Effort: MoyenImpact: Critique
🔴 Critique
Absence de validation des entrées (@Valid)
Tous les contrôleurs REST du backend-saeb

Les contrôleurs REST ne valident pas les données reçues. Des payloads malformés, des injections SQL ou des valeurs hors limites peuvent atteindre la couche service.

🟠 Haute
Absence de protection brute-force sur l'authentification
authorization-server-be · bnaauthentication

Les endpoints /api/auth/login et /auth/signin/multiple ne sont pas protégés contre les attaques par force brute. Il n'y a pas de rate limiting ni de verrouillage de compte.

RisqueTentatives illimitées de connexion sur les comptes BNA des agents.
SolutionBucket4J (rate limiting par IP/username) + verrouillage temporaire après N échecs + Spring Boot Actuator metrics.
// Rate limiting avec Bucket4J @PostMapping("/api/auth/login") public ResponseEntity login(@RequestBody LoginRequest req, HttpServletRequest httpReq) { String ip = httpReq.getRemoteAddr(); if (!rateLimiter.tryConsume(ip)) { return ResponseEntity.status(429).body("Trop de tentatives"); } // ... logique auth }
Bucket4JSpring Security Effort: MoyenImpact: Élevé

Absence de journal d'audit des opérations sensibles
backend-saeb — toutes les opérations d'écriture

Les créations, modifications et suppressions de canevas, crédits et garanties ne sont pas auditées. En cas d'incident, il est impossible de savoir qui a fait quoi et quand.

SolutionSpring Data Auditing (@CreatedBy, @LastModifiedBy, @CreatedDate) + table d'audit dédiée ou AOP pour les actions critiques.

Coexistence Java 8 / Java 17 et Spring Boot 2 / Spring Boot 3
bnaauthentication (Java 8, SB 2.0.5) vs backend-saeb (Java 17, SB 3.2)

Le module bnaauthentication utilise Spring Boot 2.0.5 (EOL depuis novembre 2023) et Java 8 (EOL commercial). Cela représente des failles de sécurité non patchées et une incompatibilité grandissante avec le reste du projet.

Les endpoints retournant des listes (GET /api/canevas) renvoient vraisemblablement toutes les données sans pagination. Sur une base de données BNA en production avec des milliers de dossiers, cela peut provoquer des timeouts et une surcharge mémoire.

🟠 Haute
Remplacer ModelMapper par MapStruct
backend-saeb — MapperConfig.java · tous les services

ModelMapper utilise la réflexion à l'exécution : lent, non type-safe, et les erreurs de mapping ne sont détectées qu'au runtime. MapStruct génère du code Java à la compilation, zéro réflexion, 10-20x plus rapide.

// MapStruct — génération à la compilation @Mapper(componentModel = "spring") public interface CanevaMapper { CanevaDto toDto(Caneva entity); Caneva toEntity(CanevaDto dto); List<CanevaDto> toDtoList(List<Caneva> entities); @Mapping(target = "clientNom", source = "client.nom") CanevaDto toDtoWithClient(Caneva entity); } // pom.xml dependency <artifactId>mapstruct</artifactId><version>1.5.5.Final</version>
MapStructAPT Effort: MoyenImpact: Performance + Type Safety

🟠 Haute
Risque de fuites mémoire — Observables non désabonnés
Tous les composants Angular utilisant subscribe()

Si les composants Angular utilisent .subscribe() sans désabonnement dans ngOnDestroy, chaque navigation crée des souscriptions fantômes qui restent en mémoire et déclenchent des appels HTTP sur des composants détruits.

// RISQUE — subscribe sans cleanup this.canevaService.getAll().subscribe(data => this.canevas = data); // BONNE PRATIQUE — takeUntilDestroyed (Angular 16+) private destroyRef = inject(DestroyRef); this.canevaService.getAll() .pipe(takeUntilDestroyed(this.destroyRef)) .subscribe(data => this.canevas = data); // Ou AsyncPipe dans le template (désabonnement automatique) // canevas$ = this.canevaService.getAll() // Template: *ngFor="let c of canevas$ | async"
takeUntilDestroyedAsyncPipe Effort: MoyenImpact: Stabilité
🟠 Haute
Absence d'intercepteur global d'erreurs HTTP
_helpers/auth.interceptor.ts — gestion erreurs manquante

L'intercepteur actuel injecte le JWT mais ne gère pas les erreurs HTTP globalement (401 → redirect login, 403 → message, 500 → toast, réseau → retry). Chaque service doit gérer ses propres erreurs.

@Injectable() export class ErrorInterceptor implements HttpInterceptor { intercept(req: HttpRequest<any>, next: HttpHandler): Observable<HttpEvent<any>> { return next.handle(req).pipe( retry({ count: 1, delay: 1000 }), // 1 retry sur erreur réseau catchError((err: HttpErrorResponse) => { if (err.status === 401) this.auth.logout(); if (err.status === 403) this.toast.warn('Accès refusé'); if (err.status >= 500) this.toast.error('Erreur serveur'); return throwError(() => err); }) ); } }

4 points
🔴 Critique
Aucun outil de migration de schéma (Flyway / Liquibase)
sqlSchema · V1_gpt__Initial_schema.sql — scripts manuels

Les scripts SQL sont appliqués manuellement. Sans outil de migration, il est impossible de savoir quelle version du schéma est appliquée sur quel environnement, et les migrations en équipe créent des conflits.

Risques actuelsSchéma prod différent du schéma dev. Rollback impossible. Historique des changements perdu. Migrations non rejouables.

# Structure Flyway recommandée src/main/resources/db/migration/ ├── V1__initial_schema.sql ├── V2__add_credit_indexes.sql ├── V3__add_audit_columns.sql └── V4__add_garantie_table.sql # application.properties spring.flyway.enabled=true spring.flyway.locations=classpath:db/migration spring.flyway.baseline-on-migrate=true

Documenter et optimiser les index Oracle
Tables CANEVAS_AGRICOLE · CREDIT_* · GARANTIE_*

Les requêtes fréquentes de recherche de canevas par agent (matricule), par client, par date et par statut n'ont pas d'index documentés. Sur une table avec des milliers de dossiers, les full table scans dégradent les performances.

4 points
Observabilité = Logs + Métriques + Traces distribuées. Sans ces 3 piliers, diagnostiquer un incident en production sur ce système multi-services est très difficile.

Logging structuré (JSON) centralisé
Tous les services Spring Boot
