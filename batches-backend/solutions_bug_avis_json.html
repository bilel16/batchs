🐛 Bug — donnees_avis_json vide dans le snapshot

Analyse complète + 3 solutions avec avantages/inconvénients + emplacements exacts dans le code

🔍 Pourquoi le bug se produit

Quand on appelle POST /api/avis, voici ce qui se passe avec les transactions de base de données :

═══ TRANSACTION T1 (AvisService.saveAvis) ══════════════════════════════ │ ├─ ✔ avisRepository.save(avis) │ └→ L'avis est en mémoire (JPA cache), pas encore écrit en BDD │ ├─ ✔ updateCaneva(...) │ └→ Mise à jour du canevas, toujours dans T1 │ ├─ ✔ snapshotService.createSnapshot(...) ← appel │ │ ╔═══ TRANSACTION T2 (REQUIRES_NEW) ═════════════════════════════════╗ │ ║ @Transactional(propagation = Propagation.REQUIRES_NEW) ║ │ ║ └─ T2 est une transaction SÉPARÉE — T1 est en pause ║ │ ║ ║ │ ║ buildAvisJson(canevasId) ║ │ ║ └─ avisRepository.findAllByNumCaneva(canevasId) ║ │ ║ └─ LIT DEPUIS LA BDD ║ │ ║ → L'avis de T1 n'est PAS encore committé ! ║ │ ║ → donnees_avis_json = [] (vide) ║ │ ╚═══════════════════════════════════════════════════════════════════╝ │ └─ return savedDTO [T1 committe ici — trop tard pour le snapshot déjà créé]
⚠️ Deuxième problème (bug bonus) : Dans buildAvisJson() à la ligne 537, il y a du code de débogage non professionnel qui doit être nettoyé : System system = null; system.out.println(...) (accès à un champ statique via une variable nulle — mauvaise pratique).
Solution 1

Changer REQUIRES_NEW → REQUIRED ⭐ La plus simple

La cause est que createSnapshot() s'exécute dans une nouvelle transaction séparée (REQUIRES_NEW) qui ne peut pas voir les données non commitées de T1. En changeant pour REQUIRED (valeur par défaut de Spring), le snapshot s'exécute dans la même transaction que saveAvis(), et voit donc l'avis qui vient d'être sauvegardé.

✅ Avantages

  • 1 seule ligne à changer dans un seul fichier
  • Le snapshot voit immédiatement le nouvel avis
  • Aucun risque de régression sur les autres endpoints
  • Solution la plus rapide à mettre en place
  • Facile à comprendre pour un débutant

❌ Inconvénients

  • Si createSnapshot() plante → toute la transaction est annulée (l'avis sauvegardé est aussi perdu)
  • Perd l'isolation : si le snapshot prend du temps, il bloque T1
  • Si createSnapshot() est appelé depuis d'autres services en dehors d'une transaction, cela pourrait changer le comportement

Solution 2

Construire le JSON des avis dans T1 et l'utiliser dans le snapshot ⚖️ Meilleur équilibre

Au lieu de laisser createSnapshot() relire la BDD (dans T2), on construit la liste complète des avis dans T1 (où le nouvel avis est visible), et on la passe directement au snapshot. On garde REQUIRES_NEW pour l'isolation.

Note importante : actuellement, le paramètre avisJson est déjà envoyé à createSnapshot() depuis AvisService, mais il n'est jamais utilisé (le code appelle quand même buildAvisJson(canevasId) en ignorant ce paramètre). Cette solution corrige ce problème.

✅ Avantages

  • Garde l'isolation (REQUIRES_NEW) entre les deux transactions
  • Si le snapshot échoue, l'avis est quand même sauvegardé
  • Résout le bug sans changer la logique transactionnelle
  • Utilise enfin le paramètre avisJson qui était déjà prévu

❌ Inconvénients

  • Modifications dans deux fichiers au lieu d'un
  • Il faut ajouter une méthode helper dans AvisService
  • Le JSON est construit deux fois (une fois dans AvisService, une fois si fallback)
  • Un peu plus de code à comprendre pour un débutant

Solution 3

Utiliser @TransactionalEventListener 🏗️ La plus propre architecturalement

Au lieu d'appeler directement createSnapshot() depuis saveAvis(), on publie un événement Spring après la sauvegarde de l'avis. Le snapshot est créé seulement après le commit de T1, donc il peut lire l'avis en toute sécurité.

✅ Avantages

  • Parfaitement isolé : snapshot créé APRÈS le commit de l'avis
  • Séparation des responsabilités (principe SOLID)
  • Si le snapshot échoue, l'avis est déjà sauvegardé en BDD
  • Facilement extensible (d'autres listeners peuvent écouter le même événement)

❌ Inconvénients

  • La plus complexe à implémenter (3 fichiers + 1 nouveau fichier)
  • Déconseillée pour un débutant sans expérience Spring Events
  • Le snapshot est asynchrone par rapport au retour de l'API → si le frontend recharge le snapshot immédiatement, il peut ne pas encore exister
  • Debugging plus difficile (flux indirect)

✅ Recommandation finale

En tant que développeur débutant sur ce projet, voici l'approche conseillée :

1

Appliquer la Solution 1 maintenant (5 minutes) : changer @Transactional(propagation = Propagation.REQUIRES_NEW) en @Transactional dans CanevasSnapshotService.java ligne 52.

C'est suffisant pour résoudre le bug. Le risque est acceptable : si le snapshot échoue, Spring affiche un warning dans les logs (le try/catch dans AvisService ligne 268 l'attrape déjà).

2

Nettoyer le code de debug (2 minutes) : dans CanevasSnapshotService.java lignes 537–538, remplacer les deux lignes par log.info("buildAvisJson: {} avis trouvés pour canevasId={}", avisList.size(), canevasId);

3

Plus tard, si vous avez le temps : migrer vers la Solution 2 qui offre une meilleure isolation (l'avis est sauvegardé même si le snapshot échoue). La Solution 3 est réservée à une refactorisation avancée.
