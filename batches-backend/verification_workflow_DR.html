VÉRIFICATION — Boule DR : Bleue → Verte (Workflow Journal)

Analyse du comportement réel vs comportement attendu pour les étapes P3 / P4 de la Direction Régionale

BUG IDENTIFIÉ · ligne 117 snapshot-history.component.ts PEC_AVIS_DEC dans step3done Correction disponible

📋1. Les deux étapes DR concernées

Étape P3 — Directeur PEC Avis (PROFILE3 · Page 3)

  • Action : Prise en charge de la phase d'opinion
  • Stade résultant : PEC_AVIS_DEC
  • Action log : PRENDRE_EN_CHARGE
  • Signification : Le directeur régional reconnaît avoir reçu le canvas et commence l'analyse — travail en cours, pas terminé
  • Boule attendue : BLEUE (active, pulsante)

Étape P4 — Directeur Validation Avis (PROFILE4 · Page 4)

  • Action : Émission de l'avis formel DR (FAVORABLE / DÉFAVORABLE)
  • Stade résultant : VALIDER_DR
  • Action log : VALIDER
  • Signification : Le directeur a rendu sa décision ET le canvas est envoyé au centrale — travail DR terminé
  • Boule attendue : BLEUE jusqu'à envoi central, puis VERTE ✓
ℹ️
Règle métier visée : La "boule Direction Régionale" dans le stepper du Journal Workflow doit rester BLEUE (en cours) tant que P3 seul a agi. Elle ne passe au VERT (terminé) que lorsque P4 a validé l'avis ET le canvas a été transmis au pôle central (affectation vers commission).

Note sur PEC_AVIS_DEC → 'warning' (orange) : Dans statusSeverity(), le statut PEC_AVIS_DEC est mappé à warning (orange). C'est cohérent pour l'affichage du badge de statut du snapshot individuel (indique "en attente/en cours de décision"). 🚨8. Anomalie supplémentaire — VALID_AVIS_DEC non utilisé

Stade VALID_AVIS_DEC défini mais jamais assigné

L'enum Stade.java déclare la valeur VALID_AVIS_DEC (ligne 18) mais aucun service backend ne l'assigne jamais. Le code de P4 (AvisService.java) utilise VALIDER_DR à la place :

❌ Stade déclaré mais orphelin
// Stade.java — enum
VALID_AVIS_DEC, // ← déclaré...
// AvisService.java — jamais utilisé :
// caneva.setStade(Stade.VALID_AVIS_DEC);
// ← cette ligne n'existe nulle part
❌ Ce qui est réellement utilisé par P4
// AvisService.java · ligne 166
caneva.setStade(Stade.VALIDER_DR);
// ^ P4 assigne VALIDER_DR, pas VALID_AVIS_DEC
// WorkflowLog action créée :
action = "VALIDER"
statusAtSnapshot = "VALIDER_DR"
⚠️
Impact : Le frontend utilise bien hasStatus('VALIDER_DR') dans step3done pour détecter la validation P4 — ce qui correspond correctement à ce que le backend assigne. La confusion vient du nom VALID_AVIS_DEC mentionné dans la documentation mais qui n'est jamais assigné. À terme : soit supprimer VALID_AVIS_DEC de l'enum (deadcode), soit unifier les noms.

📌9. Résumé de la vérification

Réponse à la question : "La boule DR reste-t-elle bleue jusqu'à ce que P4 valide ET que le canvas passe au centrale ?"

  1. Non — il y a un bug. La boule DR passe au VERT dès que P3 agit (PEC_AVIS_DEC), bien avant que P4 n'émette son avis. → Fichier : snapshot-history.component.ts · ligne 117
  2. La cause : hasStatus('PEC_AVIS_DEC') est inclus dans step3done. Ce stade signifie "en cours" (P3 a pris en charge) mais est interprété comme "terminé" par le stepper.
  3. Double condition manquante : Le code actuel ne vérifie pas que le canvas a été transmis au centrale avant de marquer DR comme terminée. Il suffit que VALIDER_DR soit présent — pas besoin que PEC_CHARGEE_COMM soit aussi présent.
  4. La correction : Remplacer ligne 117 par const step3done = drValidated && sentToCentral où drValidated = VALIDER_DR et sentToCentral = un stade de commission est présent.
  5. Anomalie secondaire : VALID_AVIS_DEC est déclaré dans l'enum Stade mais jamais assigné par le backend. Nettoyage recommandé.
