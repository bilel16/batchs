🏗️ 1. Vue d'ensemble de l'architecture

Qu'est-ce que PGCANVAS ?

PGCANVAS est un système de gestion de canvas agricoles (dossiers de demande de crédit agricole). Une agence bancaire reçoit une demande client, crée un "canvas", puis ce dossier passe par une chaîne de validation multi-niveaux — de l'agent de terrain jusqu'à la commission centrale — avant d'obtenir une décision finale (favorable ou défavorable).

Backend — Spring Boot

  • Framework : Spring Boot 3.2.2, Java 21
  • Base de données : Oracle (multi-datasource)
  • Sécurité : OAuth2 + JWT via Keycloak
  • Port : 8081
  • Mapping : MapStruct + Spring Data JPA
  • Cache : Caffeine (données BNA/BCT)

Frontend — Angular

  • Framework : Angular (PrimeNG UI)
  • 9 pages/profils distincts
  • Routing par profil (CCA, CHAGCE, PROFILE3…)
  • Services HTTP pour chaque domaine
  • Gestion des rôles côté menu

Entités principales

  • Caneva — Le dossier central
  • CanevasUser — Utilisateurs & rôles
  • Affectation — Assignation de dossier
  • CanevasStructureSnapshot — Versionnement
  • CanevasWorkflowLog — Audit trail
  • Avis — Décisions/opinions

Niveaux organisationnels

  • AGC — Agence (Type 1)
  • DR — Direction Régionale (Type 2)
  • DC — Direction Centrale (Type 5)
  • Postes commission : 00, 76, 06, 04, 07

Hiérarchie organisationnelle & superviseur

La table CANEVA_USER implémente une hiérarchie auto-référentielle via les champs superviseur (parent) et subordonnes (enfants). Cela permet :

  • Qu'un superviseur voit les canvas de tous ses subordonnés (récursivement)
  • La délégation de tâches dans l'arbre hiérarchique
  • Le filtrage des listes par périmètre de responsabilité
// CanevasUser.java — Hiérarchie auto-référentielle
@ManyToOne
@JoinColumn(name = "superviseur_id")
private CanevasUser superviseur;

@OneToMany(mappedBy = "superviseur", fetch = FetchType.LAZY)
private Set<CanevasUser> subordonnes;

// Attribut discriminant pour les droits et l'affectation
private String libelleStructure;  // ex: "CHARGÉ", "AGC", "DR", "DC"
private String codeStructure;     // code organisationnel (AGC001, DR002...)

⚡ 5. Workflow complet étape par étape

CCA
Agence

Étape 1 — Prise en charge initiale (CHARGÉ D'AFFAIRES)

PRISE_EN_CHARGE → INIT_DONNEE Page 1 · Profil CCA Snapshot v1

Le Chargé d'Affaires (CCA) de l'agence reçoit la demande client. Il recherche le client par numSeqpers, crée le canvas et saisit toutes les données initiales : sites agricoles sélectionnés, types de crédits demandés (terrain, investissement, court terme), documents justificatifs. Le stade passe à INIT_DONNEE et un Snapshot v1 est créé.

Actions : CRÉER CANVAS SAISIR DONNÉES JOINDRE DOCUMENTS SOUMETTRE
CHAGCE
Chef Agence

Étape 2 — Validation données (CHEF AGENCE)

PEC_DONNEE → VALID_DONNEE Page 2 · Profil CHAGCE Snapshot v2

Le Chef d'Agence reçoit le canvas dans sa file de travail (liste filtrée par codeStructure + stade). Il consulte toutes les données saisies, peut les enrichir, et émet sa décision : VALIDER (passe à VALID_DONNEE) ou CORRIGER (retourne au CCA avec état CORRIGE_DONNEE). En cas de validation, un Snapshot v2 est créé et le canvas remonte à la Direction Régionale.

Actions : PRE_VALIDER CORRIGER VALIDER
DIR P3
Direction Rég.

Étape 3 — Prise en charge avis (DIRECTEUR — PEC AVIS)

EN_COURS_ETUDE → PEC_AVIS_DEC Page 3 · Profil PROFILE3

Le Directeur Régional — profil PROFILE3 — reçoit les canvas validés par les agences de sa région. Il prend en charge la phase d'opinion : le canvas passe de EN_COURS_ETUDE à PEC_AVIS_DEC. Cette étape matérialise la prise de connaissance formelle avant l'émission de la décision. Une affectation est créée vers le directeur PROFILE4.

Actions : PRENDRE_EN_CHARGE CONSULTER_DONNÉES
DIR P4
Direction Rég.

Étape 4 — Validation avis / opinion (DIRECTEUR — VALIDATION AVIS)

PEC_AVIS_DEC → VALID_AVIS_DEC Page 4 · Profil PROFILE4 Snapshot v3

Le Directeur — profil PROFILE4 — émet l'avis formel de la Direction Régionale. Il saisit les données d'avis (montants proposés, conditions, observations) et choisit : FAVORABLE ou DÉFAVORABLE. En cas de correction, l'état passe à CORRIGE_AVIS_DEC. Un Snapshot v3 est créé avec la valeur d'avis. Le canvas est ensuite transmis à la Direction Centrale.

Actions : VALIDER CORRIGER REFOULER
ADMIN P5
Dir. Centrale

Étape 5 — Affectation vers la commission (ADMIN / CENTRALE)

VALID_AVIS_DEC → PEC_CHARGEE_COMM Page 5 · Profil PROFILE5

L'administrateur central (PROFILE5 — Page 5) reçoit les canvas validés par les DR. Il affecte le canvas à un intervenant de la commission centrale. La logique d'affectation est déterminée par le libelleStructure du destinataire :

  • Si destinataire = "CHARGÉ" → etatAffectation = AFFECTE (immédiat)
  • Sinon → etatAffectation = EN_COURS_ETUDE (en attente)

Une notification email est envoyée au destinataire. Le canvas prend l'état PEC_CHARGEE_COMM.

Actions : CRÉER_AFFECTATION CHOISIR_INTERVENANT ENVOYER_EMAIL
COMM P6
Poste 00/76

PEC_CHARGEE_COMM Page 6 · Profil PROFILE5 Snapshot v4

L'agent affecté au Poste 00 ou 76 prend en charge le canvas au niveau "Chargée Commission". Il analyse le dossier complet (données, engagements BNA/BCT, classes, crédits, garanties) et formule un avis. Un Snapshot v4 est créé avec ses observations. Le dossier remonte ensuite au niveau Division.

Actions : ANALYSER SAISIR_AVIS VALIDER
COMM P7
Poste 06

Étape 7 — Division Commission (Poste 06)

PEC_DEVISION_COMM Page 7 · Profil PROFILE5 Snapshot v5

Le chef de Division (Poste 06) examine à son tour le canvas et les avis accumulés (chargée + directeur). Il produit sa propre analyse et valide ou renvoie. Snapshot v5 créé. Transmission au niveau Département.

Actions : ANALYSER SAISIR_AVIS VALIDER REFOULER
COMM P8
Poste 04

Étape 8 — Département Commission (Poste 04)

PEC_DEP_COMM Page 8 · Profil PROFILE5 Snapshot v6

Le Département (Poste 04) constitue le troisième niveau d'examen à la commission. Il synthétise les avis précédents et donne sa recommandation. Snapshot v6. Transmission finale à la Commission Centrale.

Actions : SYNTHÉTISER SAISIR_AVIS VALIDER
COMM P9
Poste 07

Étape 9 — Commission Centrale — DÉCISION FINALE (Poste 07)

VALID_CENTRALE_COMM Page 9 · Profil PROFILE5 Snapshot v7 (FINAL)

La Commission Centrale (Poste 07) est l'instance décisionnaire finale. Elle examine l'ensemble du dossier (7 versions de snapshot, tous les avis des niveaux précédents) et émet la décision définitive : FAVORABLE ou DÉFAVORABLE. Le Snapshot v7 est créé avec le statut VALID_CENTRALE_COMM et la valeur d'avis finale. Le canvas est clôturé.

Actions : DÉCISION_FINALE AVIS=FAVORABLE AVIS=DEFAVORABLE CLÔTURER
⚠️
Retours en arrière (CORRIGER / REFOULER) : À chaque étape, l'intervenant peut renvoyer le dossier à l'étape précédente via l'action CORRIGER (pour demande de complément/correction) ou REFOULER (pour refus formel). Ces transitions inversent le stade (ex: CORRIGE_DONNEE, CORRIGE_AVIS_DEC) et une entrée CanevasWorkflowLog est créée avec l'action correspondante et les commentaires.

📋 6. Logique d'affectation (Affectation)

Création d'une affectation

Lorsqu'un intervenant affecte un canvas à un autre :

  1. Le système récupère le libelleStructure du destinataire
  2. Si "CHARGÉ" → etatAffectation = AFFECTE
  3. Sinon → etatAffectation = EN_COURS_ETUDE
  4. L'émetteur (matriculeEmetteur) et le récepteur (matriculeRecepteur) sont enregistrés
  5. Une notification email est envoyée

Affectation la plus récente = intervenant courant

Pour déterminer qui traite actuellement le canvas, le système lit la dernière affectation active en base. Le matriculeRecepteur de cette affectation est l'intervenant courant. Les recherches par structure utilisent codeStructureRecepteur.

Vue superviseur — Cascade hiérarchique

La méthode getCanevasBySuperviseurAndSubordonnes(superviseurId) :

  1. Récupère tous les subordonnés récursivement
  2. Filtre les affectations actives pour chaque subordonné
  3. Retourne uniquement la dernière affectation par canvas
  4. Permet au superviseur de voir tout son périmètre
// AffectationServiceImpl.java — Logique de détermination de l'état
public Affectation createAffectation(AffectationDto dto) {
    CanevasUser recepteur = userRepo.findById(dto.getCanevaUserId()).orElseThrow();
    String libelleStructure = recepteur.getLibelleStructure();

    // Détermination automatique de l'état selon le rôle du destinataire
    if ("CHARGÉ".equals(libelleStructure)) {
        affectation.setEtatAffectation(EtatAffectation.AFFECTE);
    } else {
        affectation.setEtatAffectation(EtatAffectation.EN_COURS_ETUDE);
    }

    // Traçabilité émetteur / récepteur
    affectation.setMatriculeEmetteur(dto.getMatriculeEmetteur());
    affectation.setCodeStructureEmetteur(dto.getCodeStructureEmetteur());
    affectation.setMatriculeRecepteur(recepteur.getMatricule());
    affectation.setCodeStructureRecepteur(recepteur.getCodeStructure());

    // Notification email
    sendEmailNotification(recepteur.getEmail(), caneva);

    return affectationRepo.save(affectation);
}

📸 8. Snapshots & traçabilité

Principe du versionnement par snapshot

À chaque transition significative du workflow, le système crée un snapshot immuable de l'état complet du canvas. Ce snapshot contient :

  • L'état (statusAtSnapshot) au moment de la capture
  • Le code et libellé de la structure qui a créé le snapshot
  • La matricule de l'opérateur
  • Les observations/commentaires
  • L'ensemble des données JSON (engagements, crédits, garanties, avis) — champs LOB
  • Un numéro de version incrémental (versionNumber)

v2Chef AgenceValidation donnéesVALID_DONNEEv1 + données enrichies + engagements BNA/BCT

CanevasWorkflowLog — Journal d'audit

// WorkflowLogService.java — Enregistrement de chaque transition
public void log(Long canevasId, String fromStructure, String toStructure,
                String action, String performedBy, String comments,
                Integer snapshotVersion, String structureMere) {
    CanevasWorkflowLog entry = new CanevasWorkflowLog();
    entry.setCanevasId(canevasId);
    entry.setFromStructure(fromStructure);     // Structure source
    entry.setToStructure(toStructure);         // Structure destination
    entry.setAction(action);                   // VALIDER, PRE_VALIDER, REFOULER, CORRIGER, ANNULER
    entry.setPerformedBy(performedBy);         // Matricule de l'opérateur
    entry.setPerformedAt(LocalDateTime.now());
    entry.setComments(comments);
    entry.setSnapshotVersion(snapshotVersion);
    entry.setStructureMere(structureMere);     // Hiérarchie parente (pour filtrage)
    workflowLogRepo.save(entry);
}

Filtrage de l'historique selon le rôle

La méthode getHistoryFiltered(canevasId, typeStructure, codeStructure) adapte la visibilité selon le niveau organisationnel :

  • Type "1" (AGC — Agence) : voit uniquement ses propres logs (fromStructure = codeStructure)
  • Type "2" (DR — Rég.) : voit ses logs + tous les logs des agences enfants (structureMere = codeStructure)
  • Type "5" (DC — Centrale) : voit tous les logs sans restriction

// CanevasSnapshotService.java — Contrôle d'accès basé sur la structure
public boolean canAccessCanvas(String matricule, String codeStructure,
                               String typeStructure, Long canevasId) {
    switch (typeStructure) {
        case "1":  // AGC — voit uniquement ses propres canvas
            return canevasRepo.existsByIdAndCodeStructure(canevasId, codeStructure);
        case "2":  // DR — voit les canvas de toutes ses agences enfants
            return canevasRepo.existsByIdAndStructureMere(canevasId, codeStructure);
        case "5":  // DC — accès total
            return true;
        default:
            return false;
    }
}

🔒 11. Sécurité & Authentification

Endpoints publics

📌 12. Synthèse — Règles métier clés

Règle 1 — Avancement séquentiel obligatoire

Le canvas ne peut pas sauter une étape. Chaque stade débloque le suivant uniquement si l'action est accomplie par le bon profil dans la bonne structure. La machine d'état est vérifiée côté backend.

Règle 2 — Traçabilité totale

Chaque action crée simultanément : un CanevasWorkflowLog + un Snapshot (gel des données). Aucune modification n'est perdue. L'historique est accessible par version et filtré selon le rôle.

Règle 3 — Affectation = propriété courante

L'affectation la plus récente détermine qui détient actuellement le canvas. Le système interroge toujours la dernière affectation active pour afficher les listes de travail.

Règle 4 — libelleStructure = déterminant de l'état

Si libelleStructure == "CHARGÉ" → affectation immédiate avec état AFFECTE. Sinon l'état est EN_COURS_ETUDE. Ce champ est le pivot de la logique d'affectation.

Règle 5 — Visibilité hiérarchique des données

AGC (Type 1) ne voit que ses canvas. DR (Type 2) voit les canvas de toutes ses agences via structureMere. DC (Type 5) voit tout. Ce filtrage s'applique aux listes ET à l'historique.

Règle 6 — Décision finale = commission centrale

Seule la Commission Centrale (Poste 07, Page 9) émet la décision définitive enregistrée comme VALID_CENTRALE_COMM. Tous les avis précédents sont consultatifs. Le canvas est clôturé après cette étape.
