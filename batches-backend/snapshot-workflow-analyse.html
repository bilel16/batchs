🏗 1. Contexte Métier et Architecture

Le module Snapshot Workflow est le cœur du système de validation des dossiers de crédit agricole de la BNA (Banque Nationale Agricole, Tunisie). Il permet de tracer chaque état d'un dossier (appelé canvas) tout au long de son circuit de validation, de l'agence locale jusqu'à la décision finale de la direction centrale.

Qu'est-ce qu'un Snapshot ?

Un snapshot est une photographie complète et immuable du dossier à un instant précis. Chaque fois qu'une action workflow est effectuée (validation, refoulement, prise en charge), un snapshot est créé. Cela permet de :

  • Conserver l'historique complet des modifications du dossier
  • Comparer l'état d'un dossier à différents moments
  • Assurer la traçabilité et la conformité bancaire (audit)
  • Permettre à chaque niveau hiérarchique de voir l'état du dossier à son arrivée

Architecture technique

SnapshotHistoryComponent — Composant principal UI (Angular Signals)
SnapshotService — Couche HTTP vers l'API REST backend
GET /api/canevas/{id}/snapshots → liste des versions
GET /api/canevas/{id}/snapshots/{sid}/detail → détail complet
GET /api/canevas/{id}/snapshots/workflow-log → journal des actions
POST /api/canevas/{id}/valider → valider + transmettre
POST /api/canevas/{id}/refouler → refouler le dossier
CanevasAgrService — Signal contenant l'ID du canvas courant
UserService — Signal contenant le profil utilisateur connecté

✏ ÉTAPE 1 — Saisie à l'Agence Condition : snapshots.length > 0

Acteur : Agent Agence (typeStructure = '1')

Ce qui se passe : L'agent saisit toutes les informations du dossier agricole dans le canvas. Une fois les données complètes, il enregistre — ce qui déclenche la création du premier snapshot en base de données avec le statut initial.

Données capturées dans le snapshot :

  • creditsData : Crédits CT (court terme), investissement, achat terrain — avec montants par ligne de crédit
  • engagementsBNA : Engagements en cours à la BNA (type risque, autorisé, encours, impayé)
  • engagementsBCT : Engagements déclarés à la Banque Centrale de Tunisie
  • exploitationData : Sites géographiques d'exploitation, projets CT (barème, CA réalisé, CA prévisionnel, 3 mois achat)
  • garantiesData : Garanties proposées (hypothèques, nantissements, cautions)
  • engagementDetaille : Actionnaires, premier responsable, groupe, vendeurs
📌 Cas Réel — Dossier d'un agriculteur de Béja

Fatma Bouazizi, agricultrice à Testour (Béja), dépose une demande de crédit CT de 85 000 TND pour sa production d'olivier et un crédit d'investissement de 120 000 TND pour un tracteur. L'agent de l'agence AGC-059 saisit les données : 1 site d'exploitation (Délégation Testour, lat/long inclus), encours BNA existant de 15 000 TND, barème olive = 450 TND/ha × 50 ha = 22 500 TND. Le premier snapshot v1 est créé automatiquement avec statusAtSnapshot = 'SAISIE_INITIALE'.

✓ ÉTAPE 2 — Validation Chef Agence Condition : has('PRE_VALIDER') || hasStatus('VALID_DONNEE')

Acteur : Chef Agence (typeStructure = '2')

Ce qui se passe : Le chef agence examine le dossier soumis. Il peut le valider et le transmettre à la Direction Régionale, ou le refouler vers l'agence pour corrections.

Actions possibles :

ActionStatut résultantDestinationSnapshot créé ?
PRE_VALIDER VALID_DONNEE Direction Régionale ✅ Oui (nouvelle version)
REFOULER CORRIGE_DONNEE Retour Agence ✅ Oui (motif obligatoire)
📌 Cas Réel — Refoulement pour montant incohérent

Le chef agence Kamel Nasri examine le dossier de Fatma. Il remarque que le barème calculé donne 22 500 TND mais le crédit sollicité est de 85 000 TND — un écart non justifié. Il clique sur Refouler, saisit le motif : "Montant CT sollicité dépasse le barème calculé de 62 500 TND. Veuillez justifier ou corriger." Le snapshot v2 est créé avec status=CORRIGE_DONNEE, fromStructure='AGC-059', toStructure='AGC-059'. L'agent reçoit la notification et corrige les données.

📌 Cas Réel — Validation et transmission DR

Après correction par l'agent, le chef agence re-examine le dossier. Les montants sont maintenant cohérents. Il saisit dans le formulaire "Valider & Transmettre" : toStructureCode='DR-05', avis='FAVORABLE', observations='Dossier complet, agriculteur sérieux avec 10 ans d'ancienneté'. Snapshot v3 créé avec status=VALID_DONNEE.

🔍 ÉTAPE 3 — Analyse Direction Régionale Condition : has('VALIDER') || hasStatus('VALIDER_DR') || hasStatus('PEC_AVIS_DEC')

Acteur : Direction Régionale (typeStructure = '3' ou '2' selon config)

Ce qui se passe : Le gestionnaire régional analyse le dossier en profondeur : vérification des engagements BNA/BCT, viabilité du projet, cohérence des garanties, classification du client. Il peut émettre un avis (favorable/défavorable/sans avis) avant de transmettre à la Direction Centrale.

Actions possibles :

ActionStatut résultantDestinationNotes
PRENDRE_EN_CHARGE PEC_AVIS_DEC (même structure) Marque la prise en charge sans transmission
VALIDER VALIDER_DR Direction Centrale Transmet avec avis
REFOULER CORRIGE_AVIS_DEC Chef Agence / Agence Retour pour complément d'information
📌 Cas Réel — Analyse et avis défavorable partiel

Le directeur régional de DR-05 examine le dossier. Il consulte les engagements BCT : le client a un encours de 240 000 TND dans d'autres banques. La classeBNA indique "Classe 2" en 2024-03 (douteux). Il transmet à la Direction Centrale avec avis='DEFAVORABLE', observations='Encours BCT élevé + classe BNA dégradée en 2024. Recommande plafonnement CT à 40 000 TND maximum.' Snapshot v4 créé, status=VALIDER_DR.

⭐ ÉTAPE 4 — Décision Direction Centrale (avec sous-étapes Commerciales) Condition : has('DECISION_FINALE') || hasStatus('DEC_FINAL_PRISE_ACCORD|REJET|VALID_CENTRALE_COMM')

Acteurs : Direction Centrale (typeStructure = '5') + Pôle Commercial (circuit interne)

Ce qui se passe : Le dossier entre dans la phase décisionnelle. Selon la complexité ou le montant, il peut passer par un circuit commercial interne avant la décision finale.

Sous-étapes du circuit commercial (Step 4 actif) :

📨
ENVOYER / ENVOYER_SUPERVISEUR Transmission vers le pôle commercial. Le superviseur peut re-router.
👤
PEC_CHARGEE_COMM → status: PEC_CHARGEE_COMM Un chargé commercial prend en charge le dossier pour analyse commerciale.
🏢
PEC_DEVISION_COMM → status: PEC_DEVISION_COMM Validation par la division commerciale (niveau intermédiaire).
🏛
PEC_DEP_COMM → status: PEC_DEP_COMM Validation par le département commercial (niveau supérieur).
✅
VALID_CENTRALE_COMM → status: VALID_CENTRALE_COMM Validation finale par la centrale commerciale. Dossier prêt pour décision.
⭐
DECISION_FINALE → status: DEC_FINAL_PRISE_ACCORD ou DEC_FINAL_PRISE_REJET La décision définitive est prise par la direction centrale. Le dossier est clôturé.
📌 Cas Réel — Accord avec plafonnement

La direction centrale reçoit le dossier de Fatma avec l'avis défavorable de la DR. Le chargé commercial analyse : "Malgré la classe 2 en mars 2024, classement stable sur 36 mois. Site exploitation vérifié sur terrain. Propose accord avec plafonnement CT à 50 000 TND." La division commerciale valide. Le département commercial approuve. La centrale commerciale émet VALID_CENTRALE_COMM. Décision finale : DECISION_FINALE avec status=DEC_FINAL_PRISE_ACCORD et observations='Accordé 50 000 TND CT — Investissement refusé.'

🗄 4. Structure des Données Snapshot

SnapshotSummary (liste d'historique)

snapshotId: number — identifiant unique du snapshot en base
versionNumber: number — numéro de version (1, 2, 3…) pour l'affichage
statusAtSnapshot: string — statut du workflow au moment du snapshot
structureCode: string — code de la structure qui a créé ce snapshot
structureLabel: string — libellé lisible (ex: "Agence Testour")
createdBy: string — nom/matricule de l'utilisateur créateur
matricule: string — matricule de l'utilisateur
createdAt: string (ISO date) — horodatage de création
observations: string — commentaire libre saisi lors de l'action

SnapshotDetail (détail complet — charge unique)

... (tout SnapshotSummary, plus :)
engagementsBNA: any[] — engagements directs du client à la BNA
engagementsBCT: any[] — engagements déclarés à la BCT (toutes banques)
classeBNA: any[] — historique de classification BNA sur 3 ans
classeBCT: any[] — classification BCT sur 3 ans
engagementDetaille: object
relation: RelationEngagement — données de la relation principale
actionnaires: EngagementPartie[] — actionnaires avec leurs propres engagements
premierResponsable: EngagementPartie | null — gérant ou responsable
groupe: EngagementPartie[] — membres du groupe économique
vendeurs: EngagementPartie[] — vendeurs de terrain (crédit achat terrain)
creditsData: object
courtTerme: array — lignes crédit CT avec produit, spéculation, montant
investissement: array — lignes crédit investissement
achatTerrain: array — lignes crédit achat terrain
exploitationData: object
sites: array — sites géographiques (gouvernorat, délégation, coords GPS)
projetCourtTerme: object — barème, caRealise, caPrevisionnel, moisAchat
garantiesData: any — données garanties (actuellement affiché en JSON brut)

🐛 8. Problèmes Identifiés et Corrections
🚨 BUG CRITIQUE #1 — Boutons d'action accessibles à TOUS les utilisateurs Sécurité

Fichier : snapshot-history.component.html, ligne 99–108

Problème : Le bloc @if (canAct()) qui contrôle l'accès aux boutons "Valider & Transmettre" et "Refouler" est commenté de manière incorrecte. Résultat : n'importe quel utilisateur, même un simple agent agence, peut déclencher une validation ou un refoulement.

<!-- @if (canAct()) { */ ← HTML invalide, ne ferme pas correctement <div class="hist-actions"> <button pButton label="Valider & Transmettre" ...></button> <button pButton label="Refouler" ...></button> </div> } --> ← Le commentaire commenté = les boutons sont TOUJOURS visibles

✅ Correction

<!-- Retirer les commentaires et restaurer le guard --> @if (canAct()) { <div class="hist-actions"> <button pButton label="Valider & Transmettre" icon="pi pi-check" class="p-button-success p-button-sm" (click)="showValidDlg.set(true)"></button> <button pButton label="Refouler" icon="pi pi-reply" class="p-button-danger p-button-sm" (click)="showRefoulDlg.set(true)"></button> </div> }

Et vérifier que canAct() dans le composant couvre tous les rôles autorisés (actuellement seulement '2' et '5', vérifier si DR='3' doit aussi valider).

🚨 BUG CRITIQUE #2 — Double chargement au démarrage (ngOnInit + effect) Logique

Fichiers : snapshot-history.component.ts, lignes 63–68 (effect) et 324–328 (ngOnInit)

Problème : Quand le canvas est déjà disponible au démarrage, ngOnInit appelle loadAll(id) ET initEffect tente aussi d'appeler loadAll(id) si activeCanevasId() === 0. Comme ngOnInit exécute activeCanevasId.set(id) avant l'effet, la condition === 0 peut ne pas protéger dans tous les cas d'exécution.

// ngOnInit — appelle loadAll si id > 0 ngOnInit(): void { const id = this.canevasAgrService.currentIdCaneva() || 0; this.activeCanevasId.set(id); if (id > 0) this.loadAll(id); // ← charge ici ... } // effect — peut aussi charger si la condition passe private initEffect = effect(() => { const id = this.canevasAgrService.currentIdCaneva(); if (id && id > 0 && this.activeCanevasId() === 0) { // ← peut se déclencher avant ngOnInit this.activeCanevasId.set(id); this.loadAll(id); // ← double chargement potentiel } });

✅ Correction — Supprimer l'effet, utiliser uniquement ngOnInit

// Supprimer initEffect complètement // ngOnInit gère le chargement initial ngOnInit(): void { const id = this.canevasAgrService.currentIdCaneva() || 0; this.activeCanevasId.set(id); if (id > 0) this.loadAll(id); const u = this.userService.user(); this.validForm.fromStructureCode = u?.codeStructure ?? ''; ... } // Si le canvas peut changer après init (navigation), utiliser takeUntilDestroyed : toObservable(this.canevasAgrService.currentIdCaneva) .pipe( filter(id => !!id && id > 0), distinctUntilChanged(), takeUntilDestroyed(this.destroyRef) ) .subscribe(id => { this.activeCanevasId.set(id); this.loadAll(id); });
⚠ BUG MAJEUR #3 — Subscriptions HTTP non nettoyées (memory leak) Mémoire

Fichier : snapshot-history.component.ts — toutes les méthodes subscribe()

Problème : Aucune subscription n'est désabonnée lors de la destruction du composant. Si l'utilisateur navigue rapidement, des callbacks HTTP peuvent s'exécuter sur un composant détruit, modifiant des signaux orphelins et provoquant des fuites mémoire ou des erreurs "ExpressionChangedAfterItHasBeenCheckedError".

✅ Correction — Utiliser takeUntilDestroyed

import { takeUntilDestroyed, DestroyRef } from '@angular/core/rxjs-interop'; export class SnapshotHistoryComponent { private destroyRef = inject(DestroyRef); private loadAll(id: number): void { this.loading.set(true); this.snapshotService.getHistory(id) .pipe(takeUntilDestroyed(this.destroyRef)) .subscribe({ next: d => { this.history.set(d); this.loading.set(false); }, ... }); this.snapshotService.getWorkflowLog(id) .pipe(takeUntilDestroyed(this.destroyRef)) .subscribe({ next: d => this.workflowLog.set(d), ... }); } }
⚠ BUG MAJEUR #4 — Callbacks HTTP imbriqués dans openCompare() et searchCanvas() Architecture

Fichier : snapshot-history.component.ts, lignes 492–508 (openCompare) et 397–422 (searchCanvas)

Problème : Les deux snapshots de comparaison sont chargés en séquence via des callbacks imbriqués ("callback hell"). Si le premier appel réussit mais le second échoue, compareLoading reste bloqué sur true indéfiniment.

// PROBLÈME — appels imbriqués this.snapshotService.getBySnapshotId(id, snap.snapshotId).subscribe({ next: old => { this.compareOldSnap.set(old); this.snapshotService.getBySnapshotId(id, latestSum.snapshotId).subscribe({ next: cur => { this.compareNewSnap.set(cur); this.compareLoading.set(false); }, error: () => this.compareLoading.set(false) // ← compareOldSnap reste défini, état incohérent }); }, error: () => this.compareLoading.set(false) });

✅ Correction — Utiliser forkJoin pour appels parallèles

import { forkJoin } from 'rxjs'; openCompare(snap: SnapshotSummary): void { ... this.compareLoading.set(true); forkJoin({ old: this.snapshotService.getBySnapshotId(id, snap.snapshotId), cur: this.snapshotService.getBySnapshotId(id, latestSum.snapshotId) }).pipe(takeUntilDestroyed(this.destroyRef)) .subscribe({ next: ({ old, cur }) => { this.compareOldSnap.set(old); this.compareNewSnap.set(cur); this.compareOldLabel.set(`Snapshot v${snap.versionNumber} — ${this.fmtDate(snap.createdAt)}`); this.compareNewLabel.set(`État actuel v${latestSum.versionNumber} — ${this.fmtDate(latestSum.createdAt)}`); this.compareLoading.set(false); }, error: () => { this.compareLoading.set(false); this.compareMode.set(false); this.messageService.add({ severity: 'error', summary: 'Erreur', detail: 'Impossible de charger la comparaison' }); } }); }

Avantage supplémentaire : les deux appels sont parallèles — temps de réponse divisé par 2.

🔵 BUG MINEUR #8 — Validation du formulaire "Valider & Transmettre" incomplète Validation
