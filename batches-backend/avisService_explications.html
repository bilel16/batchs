AvisService.java — Documentation complète

Guide pour développeur débutant — Comprendre le service de gestion des avis dans un système de workflow bancaire (SAEB). Chaque section explique quoi, pourquoi et comment.

1. Introduction — À quoi sert ce service ?

Contexte métier

Ce service fait partie d'une application bancaire qui gère les dossiers de crédit (appelés canevas). Chaque dossier doit passer par plusieurs niveaux d'approbation : agence → direction régionale → centrale commerciale → décision finale.

Un Avis est l'opinion/action qu'un utilisateur (chargé de clientèle, chef d'agence, directeur régional…) pose sur un dossier à un moment donné.

Annotations Spring Boot utilisées
  • @Service — Déclare cette classe comme un service Spring (composant métier).
  • @Transactional — Toutes les méthodes s'exécutent dans une seule transaction base de données. Si une erreur survient, tout est annulé (rollback).
  • @Slf4j — Injecte automatiquement un logger log pour écrire des messages de débogage.
Une transaction, c'est comme un panier dans un supermarché : soit tous les articles passent en caisse, soit rien ne passe si un problème survient. Ici, sauvegarder l'avis ET mettre à jour le canevas se font ensemble.

Entités (tables base de données) manipulées

Avis

  • L'avis posé par un utilisateur
  • Stocke le statut, la valeur, le commentaire
  • Données JSON (crédit, garanties…)

Caneva

  • Le dossier de crédit principal
  • Contient le stade actuel
  • Assigné à un agent (matrAffectCnv)

CanevasUser

  • Un utilisateur du système
  • A un matricule, une structure
  • Peut avoir un superviseur

Affectation

  • Historique des transferts
  • Émetteur → Récepteur
  • Contient l'état et les observations

2. Structure du service — Les dépendances injectées

Le service reçoit toutes ses dépendances via le constructeur (injection de dépendances). C'est la bonne pratique Spring Boot (préférable à @Autowired sur les champs). 

public AvisService(
    AvisRepository           avisRepository,       // CRUD table Avis
    CanevaRepository         canevaRepository,      // CRUD table Caneva
    ObjectMapper             objectMapper,          // Conversion Java ↔ JSON
    CanevasUserRepository    canevasUserRepository, // CRUD table CanevasUser
    AffectationRepository    affectationRepository, // CRUD table Affectation
    CanevasSnapshotService   snapshotService,       // Crée des snapshots
    WorkflowLogService       workflowLogService     // Journalise les actions
) { ... }
Qu'est-ce qu'un Repository ?

Un Repository est une interface Spring Data JPA qui génère automatiquement les requêtes SQL. Par exemple, avisRepository.save(avis) fait un INSERT ou UPDATE en base sans écrire une seule ligne de SQL.

ObjectMapper — Le traducteur JSON

L'ObjectMapper (Jackson) convertit des objets Java en chaîne JSON et inversement. Dans ce service, les données complexes (crédit, garanties) sont stockées en base sous forme de texte JSON, puis reconstruites à la lecture.

3. La méthode principale — saveAvis(AvisDTO dto)

C'est le cœur du service. Elle fait deux grandes choses : (1) sauvegarder l'avis en base, et (2) faire avancer le workflow du dossier.

Étape 1 — Créer ou mettre à jour l'entité Avis

Le service vérifie si un avis existe déjà (via id + matricule). Si oui → mise à jour de la date de modification. Si non → création d'un nouvel avis avec la date de création. 

// Si id ET matricule fournis → on cherche l'avis existant
if (dto.getId() != null && dto.getMatricule() != null) {
    Optional<Avis> optionalAvis =
        avisRepository.findByIdAndMatricule(dto.getId(), dto.getMatricule());

    if (optionalAvis.isPresent()) {
        avis = optionalAvis.get();          // mise à jour
        avis.setDateModification(LocalDateTime.now());
    } else {
        avis = new Avis();                  // création
        avis.setDateCreation(LocalDateTime.now());
    }
} else {
    avis = new Avis();                      // création (pas d'id)
    avis.setDateCreation(LocalDateTime.now());
}
Optional<T> est un conteneur qui peut contenir ou non une valeur. C'est la façon moderne Java d'éviter les NullPointerException. isPresent() vérifie si la valeur existe, get() la récupère.

Sérialisation des données complexes en JSON

avis.setDataAchatTerrain(
    objectMapper.writeValueAsString(dto.getDataAchatTerrain())
);
// Résultat en base : "[{\"montant\":5000,\"duree\":12}, ...]"

Les champs dataAchatTerrain, dataCreditInvestissement, etc. sont des listes d'objets Java. Plutôt que de créer des tables séparées, elles sont converties en texte JSON et stockées dans une seule colonne.

Étape 2 — Logique de workflow selon le statusAvis

Après la sauvegarde, le service lit le champ statusAvis du DTO et exécute l'action correspondante. C'est un if / else if en cascade.

Zoom sur le cas "Envoyer" — 3 sous-cas possibles

Cas B — Chargé / Division (isChargedOrDivision = true)

Le système cherche le superviseur de l'utilisateur courant. Si le superviseur existe → on lui affecte le dossier. Sinon → fallback vers structureMere ou codeStructureReceptrice. 

CanevasUser currentUser = canevasUserRepository.findByMatricule(matricule)...;
if (currentUser.getSuperviseur() != null) {
    CanevasUser supervisor = canevasUserRepository.findById(superviseur.getId())...;
    updateCaneva(numCaneva, supervisor.getMatricule(),
                 supervisor.getCodeStructure(), "EN_COURS_ETUDE");
    createAffectation(...);
} else {
    // Pas de superviseur → utiliser structureMere
    String fallback = structureMere != null ? structureMere : codeStructureReceptrice;
    updateCaneva(numCaneva, null, fallback, "EN_COURS_ETUDE");
}
Cas C — Utilisateur normal (isChargedOrDivision = false)

On cherche le "chef" de la structure réceptrice via findHeadMatricule(codeStructureReceptrice), puis on affecte le dossier à ce chef.

5. Snapshot & WorkflowLog — Traçabilité du dossier

Après chaque action, deux mécanismes de traçabilité sont déclenchés : un snapshot (photo de l'état) et un workflow log (journal des actions). Ils sont optionnels : si l'un échoue, la transaction principale n'est pas annulée (les exceptions sont attrapées).

1
Résolution du statut snapshot
resolveStatusAtSnapshot(statusAvis, avisValue) traduit le statusAvis en libellé métier pour le snapshot. Exemple : "VALIDER" devient "VALIDER_DR".
2
Sérialisation de l'avis en JSON
Un Map contenant les informations clés de l'avis (statusAvis, avisValue, commentaire, structure, matricule, avisId) est converti en chaîne JSON. C'est la "donnée" stockée dans le snapshot. 
Map<String, Object> avisMap = new LinkedHashMap<>();
avisMap.put("statusAvis",  dto.getStatusAvis());
avisMap.put("avisValue",   dto.getAvisValue());
// ...
String avisJson = objectMapper.writeValueAsString(avisMap);
// Résultat : {"statusAvis":"VALIDER","avisValue":"1","commentaire":"OK",...}
3
Création du Snapshot
snapshotService.createSnapshot(...) est appelé avec :
  • numCaneva — l'identifiant du dossier
  • structureCode / structureLabel — la structure qui agit
  • matriculeLog — l'agent qui agit
  • observations — le commentaire
  • statusAtSnap — le statut traduit
  • avisJson — les données de l'avis en JSON
En retour, on récupère snapshotId et versionNumber pour les passer au WorkflowLog.
4
Résolution de l'action workflow
resolveWorkflowAction(statusAvis) traduit le statut en action métier lisible pour le log.

workflowLogService.log(...) crée une entrée dans le journal avec : le canevas concerné, la structure émettrice, la structure réceptrice, l'action effectuée, la version du snapshot, et le matricule de l'agent.
Pourquoi les exceptions sont-elles attrapées ?
try {
    var snap = snapshotService.createSnapshot(...);
    snapshotId = snap.getSnapshotId();
} catch (Exception e) {
    log.warn("Échec snapshot canevas={}", dto.getNumCaneva(), e);
    // ↑ On log l'erreur MAIS on ne relance pas l'exception.
    // Le reste de saveAvis() continue normalement.
}

Le snapshot et le workflow log sont des fonctionnalités de traçabilité, pas de fonctionnement essentiel. Si le service de snapshot est indisponible, on ne veut pas bloquer la sauvegarde de l'avis. C'est une décision de conception : tolérance aux pannes secondaires.

6. Méthodes utilitaires privées

updateCaneva(Long canevaId, String matrAffect, String codeStructure, String stade)

Met à jour trois champs du canevas en base : l'agent affecté (matrAffectCnv), la structure courante (codeStructure), et le stade (Stade.valueOf(stade)). Si un paramètre est null, le champ correspondant n'est pas modifié. 

private void updateCaneva(Long canevaId, String matrAffect,
                          String codeStructure, String stade) {
    Caneva caneva = canevaRepository.findById(canevaId)
            .orElseThrow(() -> new EntityNotFoundException("Caneva not found: " + canevaId));

    if (matrAffect   != null) caneva.setMatrAffectCnv(matrAffect);
    if (codeStructure != null) caneva.setCodeStructure(codeStructure);
    if (stade         != null) caneva.setStade(Stade.valueOf(stade));
    // Stade.valueOf("EN_COURS_ETUDE") → convertit la String en enum Stade

    canevaRepository.save(caneva);
}
createAffectation(...)

Crée un enregistrement d'historique de transfert du dossier. Selon le typeStructure, les observations sont différentes :

  • "1" = Agence → DR : "Envoi de l'agence à la direction régionale"
  • "2" = DR → Centrale : "Envoi de la direction régionale [code] vers 330"
  • "5" = Commercial interne : message selon le contexte (hiérarchie ou structure)

Cas spécial : si le récepteur est un "CHARGÉ" (détecté dans son libellé de structure), l'état de l'affectation passe à AFFECTE au lieu de l'état par défaut.

findHeadMatricule(String codeStructure)

Trouve le "responsable" d'une structure : l'utilisateur qui n'a pas de superviseur dans cette structure (= le chef de la hiérarchie). 

return users.stream()
    .filter(u -> u.getSuperviseur() == null)  // pas de superviseur = c'est le chef
    .map(CanevasUser::getMatricule)
    .findFirst()
    .orElse(null);                            // null si personne trouvé
stream() permet de traiter une liste de façon fonctionnelle. filter() garde seulement les éléments qui satisfont la condition. findFirst() retourne le premier résultat ou Optional.empty().
convertToDTO(Avis avis)

Convertit l'entité base de données (Avis) en objet de transfert (AvisDTO) pour l'API. La désérialisation JSON reconstruit les objets complexes depuis le texte stocké en base. 

// Désérialisation : JSON String → List<AvisCreditAchatTerrainDTO>
if (avis.getDataAchatTerrain() != null) {
    dto.setDataAchatTerrain(
        objectMapper.readValue(
            avis.getDataAchatTerrain(),
            new TypeReference<List<AvisCreditAchatTerrainDTO>>() {}
        )
    );
}

TypeReference<List<AvisCreditAchatTerrainDTO>> est nécessaire car Java efface les types génériques à la compilation (type erasure). Cette syntaxe préserve l'information pour Jackson.

Convention de nommage — une remarque

Les méthodes getAvisByParamss, getAvisByParamss2, getAvisByParamss3, getAvisByParamss4 ont été ajoutées progressivement. Dans un projet mature, on les regrouperait avec des paramètres optionnels ou une specification JPA, mais pour un projet en développement c'est une approche courante.

Points clés à retenir

Bonnes pratiques utilisées
  • Injection par constructeur (pas @Autowired sur champ)
  • @Transactional sur la classe entière
  • Optional pour éviter les NullPointerException
  • Snapshot/Log en try-catch : tolérance aux pannes
  • Méthodes privées avec responsabilité unique
Points d'attention
  • La chaîne if/else dans saveAvis() est longue — à refactoriser avec Strategy pattern
  • Données JSON en colonne unique = pas de requêtes SQL sur ces champs
  • Méthodes de lecture très similaires — duplication de code
  • Encodage UTF-8 à vérifier (caractères accentués dans les strings)
