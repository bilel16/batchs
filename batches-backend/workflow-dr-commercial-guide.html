🔀 Partie 2 — La Transition Direction Régionale → Circuit Commercial

Comment ça se passe concrètement ?

La DR valide le dossier avec action VALIDER

Le gestionnaire DR clique sur "Valider & Transmettre". Il saisit toStructureCode = 'DC-01' (Direction Centrale), choisit son avis (FAVORABLE / DEFAVORABLE / SANS_AVIS). Le backend crée un snapshot avec statusAtSnapshot = 'VALIDER_DR' et un log de workflow action='VALIDER', fromStructure='DR-05', toStructure='DC-01'.

La DC reçoit le dossier et décide d'envoyer au pôle commercial

Le responsable DC voit le dossier avec statut VALIDER_DR. S'il juge que le dossier nécessite une analyse commerciale approfondie (montant élevé, nouveau produit, marché à risque…), il clique sur "Envoyer" → action ENVOYER. Cela marque le début du circuit commercial.

Le chargé commercial prend en charge — PEC_CHARGEE_COMM

Un chargé commercial reçoit le dossier. Il clique "Prise en charge" → l'action PEC_CHARGEE_COMM est enregistrée. Le snapshot obtient le statut PEC_CHARGEE_COMM. C'est le moment où l'écran change de sublabel : le stepper affiche "Pôle Commercial" au lieu de "Dir. Centrale".

Escalade dans le circuit — Division → Département → Centrale

Le dossier remonte la hiérarchie commerciale : Division (PEC_DEVISION_COMM), puis Département (PEC_DEP_COMM), puis validation par la Centrale Commerciale (VALID_CENTRALE_COMM). Chaque étape crée un log et met à jour le statut du dernier snapshot.

Décision Finale — DECISION_FINALE

La Direction Centrale prend la décision avec statut final DEC_FINAL_PRISE_ACCORD ou DEC_FINAL_PRISE_REJET. Le dossier est clôturé. Le stepper passe toutes les étapes en "done" (vert).

Le moment clé : comment le frontend sait qu'on est dans la phase commerciale ?

🧠 La variable inCommercialPhase C'est une simple condition booléenne calculée dans progressSteps. Elle est vraie si au moins un statut commercial est présent dans les snapshots ET que l'étape 4 n'est pas encore terminée. Quand elle est vraie, le label de l'étape 4 change dynamiquement de "Dir. Centrale" à "Pôle Commercial".
snapshot-history.component.ts — progressSteps (lignes 101–166)
① Collecte des données
On récupère tous les logs et tous les snapshots depuis les signals. On crée des Set pour faire des recherches rapides (.has() = O(1)).
② 4 conditions booléennes
Chaque step est "terminé" si une des actions/statuts correspondants existe. C'est un OU logique (||) : n'importe laquelle des preuves suffit.
③ Détection phase commerciale
C'est LA condition centrale de cette partie. Elle est vraie si on est dans le commercial ET que la décision finale n'est pas encore prise.
④ Étape active calculée
Opérateur ternaire chaîné : on cherche la première étape non terminée. Si toutes sont faites, activeStep=5 (aucune étape active = circuit terminé).
⑤ Sublabel dynamique
Le sublabel de l'étape 4 change selon inCommercialPhase. C'est ce qui fait passer l'affichage de "Dir. Centrale" à "Pôle Commercial" sur le stepper.
progressSteps = computed((): ProgressStep[] => {
  const logs    = this.workflowLog();    // tous les logs workflow
  const snaps   = this.history();        // tous les snapshots
  const actions = new Set(logs.map(l => l.action));           // Set des actions
  const statuses = new Set(snaps.map(s => s.statusAtSnapshot)); // Set des statuts

  const has       = (a: string) => actions.has(a);  // ex: has('VALIDER')
  const hasStatus = (s: string) => statuses.has(s); // ex: hasStatus('VALIDER_DR')

  // ═══ 4 BOOLÉENS : étape terminée ou non ═══
  const step1done = snaps.length > 0;  // vrai dès qu'un snapshot existe
  const step2done = has('PRE_VALIDER')  || hasStatus('VALID_DONNEE');
  const step3done = has('VALIDER')      || hasStatus('VALIDER_DR')
                  || hasStatus('PEC_AVIS_DEC');
  const step4done = has('DECISION_FINALE')
      || hasStatus('DEC_FINAL_PRISE_ACCORD')
      || hasStatus('DEC_FINAL_PRISE_REJET')
      || hasStatus('VALID_CENTRALE_COMM');

  // ═══ DÉTECTION PHASE COMMERCIALE ═══
  // Vrai si un statut commercial est présent ET step4 pas encore finie
  const inCommercialPhase = (
      hasStatus('PEC_CHARGEE_COMM')    // chargé commercial a pris en charge
      || hasStatus('PEC_DEVISION_COMM') // passé à la division
      || hasStatus('PEC_DEP_COMM')      // passé au département
  ) && !step4done;   // ← ET la décision finale n'est pas encore rendue

  // ═══ QUELLE ÉTAPE EST EN COURS ? ═══
  // Lecture : si step1 pas fait → actif=1, sinon si step2 pas fait → actif=2, etc.
  const activeStep = !step1done ? 1
                   : !step2done ? 2
                   : !step3done ? 3
                   : !step4done ? 4 : 5;  // 5 = tout terminé

  return [
    { label: 'Saisie',    sublabel: 'Agence',      icon: 'pi pi-pencil',       done: step1done, active: activeStep === 1 },
    { label: 'Validation', sublabel: 'Chef Agence', icon: 'pi pi-check-circle', done: step2done, active: activeStep === 2 },
    { label: 'Analyse',    sublabel: 'Dir. Régionale',icon: 'pi pi-search',      done: step3done, active: activeStep === 3 },
    {
      label:    'Décision',
      sublabel: inCommercialPhase ? 'Pôle Commercial' : 'Dir. Centrale',  // ← DYNAMIQUE !
      icon:     'pi pi-star',
      done:     step4done,
      active:   activeStep === 4
    }
  ];
});

snapshot-history.component.ts — currentProgressLabel (lignes 168–196)
Cas terminal — tout terminé
Si tous les steps sont done=true → on cherche le statut final parmi les snapshots pour afficher "Accord" ou "Rejet".
Cas commercial spécifique
Ce dictionnaire traduit le code statut en libellé humain pour les sous-étapes commerciales. Chaque clé est vérifiée avec statuses.has().
Cas générique
Pour toutes les autres étapes (Saisie, Validation, Analyse), on utilise steps.find(s => s.active) pour trouver l'étape active et afficher son label.
currentProgressLabel = computed((): string => {
  const snaps   = this.history();
  const statuses = new Set(snaps.map(s => s.statusAtSnapshot));
  const steps    = this.progressSteps();

  // ① CAS TERMINAL : toutes les étapes terminées
  if (steps.every(s => s.done)) {
    if (statuses.has('DEC_FINAL_PRISE_ACCORD')) return 'Dossier traité — Accord';
    if (statuses.has('DEC_FINAL_PRISE_REJET'))  return 'Dossier traité — Rejet';
    if (statuses.has('VALID_CENTRALE_COMM'))    return 'Dossier traité — Validé Centrale Commerciale';
    return 'Dossier traité — Décision finale rendue';
  }

  // ② SOUS-ÉTAPES COMMERCIALES : libellés détaillés
  const commercialLabels: Record<string, string> = {
    'PEC_CHARGEE_COMM':  'Chargé Commercial',
    'PEC_DEVISION_COMM': 'Division Commerciale',
    'PEC_DEP_COMM':      'Département Commercial',
  };
  // Pour chaque entrée du dictionnaire, vérifier si ce statut existe
  for (const [status, label] of Object.entries(commercialLabels)) {
    if (statuses.has(status)) return `En cours — ${label}`;
  }

  // ③ CAS GÉNÉRIQUE : pour Saisie, Validation, Analyse
  const active = steps.find(s => s.active);  // trouver l'étape en cours
  if (active) return `En cours — ${active.label} (${active.sublabel})`;

  return 'En attente';
});

snapshot-history.component.ts — Méthodes d'affichage (lignes 559–606)
actionLabel()
Traduit le code technique ('PEC_CHARGEE_COMM') en texte lisible ('PEC Chargé Commercial'). Si l'action n'est pas dans la liste → retourne le code brut (fallback).

// ① TEXTE AFFICHÉ dans le badge de la timeline
actionLabel(a: string): string {
  const m: Record<string, string> = {
    VALIDER:             'Valider',
    PRE_VALIDER:         'Pré-Valider',
    REFOULER:            'Refouler',
    ENVOYER:             'Envoyer',
    PEC_CHARGEE_COMM:    'PEC Chargé Commercial',
    PEC_DEVISION_COMM:   'PEC Division Commercial',
    PEC_DEP_COMM:        'PEC Département Commercial',
    VALID_CENTRALE_COMM: 'Validation Centrale',
    DECISION_FINALE:     'Décision Finale',
    // ...autres actions
  };
  return m[a] ?? a;  // ?? = si non trouvé, retourner le code brut
}

// ② COULEUR du badge (système PrimeNG)
actionSeverity(a: string) {
  const m = {
    VALIDER:          'success',    // vert
    PRE_VALIDER:      'info',       // bleu
    REFOULER:         'danger',     // rouge
    CORRIGER:         'warning',    // orange
    PEC_CHARGEE_COMM: 'info',       // bleu
    PEC_DEP_COMM:     'warning',    // orange (niveau supérieur)
    VALID_CENTRALE_COMM: 'success', // vert
    DECISION_FINALE:  'success',   // vert
  };
  return m[a] ?? 'secondary'; // gris par défaut
}

// ③ ICÔNE affiché dans le rond de la timeline
iconForAction(a: string): string {
  if (['VALIDER','PRE_VALIDER','VALID_CENTRALE_COMM'].includes(a))
    return 'pi pi-check';   // coche ✓
  if (['REFOULER','CORRIGER'].includes(a))
    return 'pi pi-times';   // croix ✗
  if (a === 'DECISION_FINALE')
    return 'pi pi-star';    // étoile ★
  if (['PRENDRE_EN_CHARGE','PEC_CHARGEE_COMM',
       'PEC_DEVISION_COMM','PEC_DEP_COMM'].includes(a))
    return 'pi pi-inbox';  // boîte de réception
  return 'pi pi-send';     // flèche envoi (défaut)
}

🔐 Partie 6 — Filtrage des logs selon le rôle utilisateur

Tous les utilisateurs ne voient pas les mêmes logs. Un agent d'agence ne doit pas voir les échanges internes DR ↔ DC. C'est le computed signal filteredLogs qui gère cela.

Règles de filtrage

Type (typeStructure)Ce qu'il voitLogique
typeStructure = '1'
Agent / Chef Agence		 Seulement les logs où son agence est impliquée (émetteur ou destinataire) fromStructure === code || toStructure === code
typeStructure = '2'
Direction Régionale		 Les logs où sa structure est impliquée + les logs de ses agences enfants fromStructure === code || toStructure === code || structureMere === code
typeStructure = '5'
Direction Centrale		 Tous les logs Pas de filtre — retourne logs complet
Mode Consultation
(canvas != canvas courant)		 Tous les logs activeCanevasId !== currentIdCaneva → pas de filtre
snapshot-history.component.ts — filteredLogs (lignes 77–92)
Mode consultation
Si l'utilisateur regarde un canvas différent du sien (via la recherche), il voit tout. Pas de restriction en consultation externe.
Type '1' = Agence
Filtre strict : seulement les logs où son code structure apparaît en fromStructure ou toStructure. Il ne voit pas les échanges DR-DC.
Type '2' = DR
Filtre élargi : voit aussi les logs des agences enfants grâce à structureMere. Ex: DR-05 voit les logs de AGC-059 si AGC-059.structureMere = 'DR-05'.
Autres types
Retourne tous les logs sans filtre. Couvre la DC (type '5') et tout autre type non explicitement géré.
filteredLogs = computed(() => {
  const logs = this.workflowLog();       // tous les logs chargés
  const type = this.userType();           // ex: '1', '2', '5'
  const code = this.userCode();           // ex: 'AGC-059', 'DR-05'

  // ① MODE CONSULTATION : canvas différent du canvas courant
  if (this.activeCanevasId() !== this.canevasAgrService.currentIdCaneva()) {
    return logs;  // pas de filtre en consultation
  }

  // ② TYPE '1' = Agent / Chef Agence
  if (type === '1' && code)
    return logs.filter(l =>
      l.fromStructure === code || l.toStructure === code
    );

  // ③ TYPE '2' = Direction Régionale (voit aussi ses agences enfants)
  if (type === '2' && code)
    return logs.filter(l =>
      l.fromStructure === code
      || l.toStructure === code
      || l.structureMere === code    // agences sous sa responsabilité
    );

  // ④ AUTRES TYPES (DC type '5', etc.) → tout voir
  return logs;
});
📡 Partie 7 — Chargement des données : loadAll() et searchCanvas()

Quand l'utilisateur arrive sur la page ou cherche un canvas, ces deux méthodes lancent les appels HTTP vers l'API. Voici comment elles fonctionnent :

snapshot-history.component.ts — loadAll() (lignes 360–372)
loading signal
loading.set(true) → l'écran affiche un spinner. loading.set(false) dans le callback → le spinner disparaît. C'est un signal réactif.
2 appels indépendants
getHistory() charge la liste des snapshots. getWorkflowLog() charge les logs. Ils s'exécutent en parallèle (pas de await l'un après l'autre).
Problème connu
Si getWorkflowLog échoue, il n'y a pas de gestion d'erreur visible à l'utilisateur. Voir l'analyse complète bug #3.
private loadAll(id: number): void {
  this.loading.set(true);  // ← affiche le spinner

  // ① Appel 1 : liste des snapshots
  this.snapshotService.getHistory(id).subscribe({
    next:  d => {
      this.history.set(d);       // stocke dans le signal
      this.loading.set(false);  // cache le spinner
    },
    error: () => this.loading.set(false)
  });

  // ② Appel 2 : logs workflow (indépendant du premier)
  this.snapshotService.getWorkflowLog(id).subscribe({
    next:  d => this.workflowLog.set(d),  // stocke dans le signal
    error: e => console.error('WorkflowLog error', e)  // ← bug : pas de message user
  });
}
snapshot-history.component.ts — searchCanvas() (lignes 386–423)
Validation input
Vérifie que l'ID saisi est > 0 avant d'appeler l'API. Si invalide → toast warning.
getHistory avec params
En mode recherche, on passe typeStructure + codeStructure pour que le serveur vérifie si l'utilisateur a le droit d'accéder à ce canvas. Renvoie 403 si accès refusé.
Gestion erreurs HTTP
3 cas gérés : 403 (accès refusé), 404 (canvas inexistant), autre (erreur générique). Bonne pratique de gestion d'erreur.
searchCanvas(): void {
  const id = this.searchCanevasId();
  if (!id || id <= 0) {
    this.messageService.add({ severity: 'warn', detail: 'Saisissez un numéro valide' });
    return;
  }

  const u = this.userService.user();
  this.snapshotService.getHistory(id, u?.typeStructure, u?.codeStructure).subscribe({
    next: d => {
      this.activeCanevasId.set(id);     // ← met à jour l'ID actif
      this.history.set(d);
      this.selectedSnap.set(null);
      this.compareMode.set(false);
      this.loading.set(false);
      // Charge aussi les logs après succès
      this.snapshotService.getWorkflowLog(id).subscribe({
        next: logs => this.workflowLog.set(logs)
      });
    },
    error: (err) => {
      this.loading.set(false);
      if (err.status === 403)
        // → "Accès refusé"
      else if (err.status === 404)
        // → "Canvas introuvable"
      else
        // → "Erreur générique"
    }
  });
}

snapshot.service.ts Couche HTTP. Appels REST vers le backend. Contient aussi les interfaces TypeScript. Modifier ici si une URL d'API change ou si une nouvelle interface est nécessaire.

Si vous voulez ajouter une nouvelle sous-étape commerciale (ex: COMITE_CREDIT)

⚠ Points à modifier dans 3 endroits Pour ajouter l'action COMITE_CREDIT qui s'insère entre VALID_CENTRALE_COMM et DECISION_FINALE :
Dans progressSteps() — inCommercialPhase

Ajouter || hasStatus('COMITE_CREDIT') dans la condition de détection de la phase commerciale.

Dans currentProgressLabel() — commercialLabels

Ajouter 'COMITE_CREDIT': 'Comité de Crédit' dans le dictionnaire.

Dans actionLabel(), actionSeverity(), iconForAction()

Ajouter le mapping pour l'affichage dans la timeline : label = "Comité Crédit", severity = 'warning', icon = 'pi pi-users'.

Dans statusSeverity()

Ajouter 'COMITE_CREDIT': 'warning' pour que le badge statut dans la table des snapshots soit coloré correctement.
